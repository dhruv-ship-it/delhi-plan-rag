# Decisions log
Each entry: what we decided, why, and what we rejected.

## D-001 · 2026-10-14 · Standalone repo
ZoneWise lives in its own repo, separate from the TerraTime capstone. Why: keeps the resume project clean. TerraTime can call ZoneWise's API later instead of merging code. Rejected: building inside the TerraTime repo.

## D-002 · 2026-10-14 · Python + FastAPI backend, React frontend, no MERN
Why: all the AI and map libraries we need are Python. There is nothing to store in MongoDB (no users; vectors live in Chroma), and Express would only add an extra hop. Rejected: MERN.

## D-003 · 2026-10-14 · No RAG frameworks
We write chunking, hybrid search, fusion and citation checks ourselves. Why: every step stays visible and explainable, and the codebase stays small. Rejected: LangChain, LlamaIndex.

## D-004 · 2026-10-14 · Documents downloaded by hand
Source PDFs are downloaded manually and listed in data/sources.csv with URL and download date. Why: government sites are slow and change often, there are only about 12 files, and the CSV keeps the work reproducible. Rejected: scraping scripts.

## D-005 · 2026-10-14 · Python 3.12 via uv
Why: one tool manages the Python version and the dependencies, with the same commands on Windows, Mac and Linux. Rejected: system Python + pip + venv.

## D-006 · 2026-10-14 · PyMuPDF for text, read in sorted order
We read page text with PyMuPDF's `page.get_text("text", sort=True)`. Why: PyMuPDF is fast (about 940 pages in under two minutes, including table detection) and `sort=True` returns the text blocks top-to-bottom and left-to-right instead of in the order the PDF happens to store them, which is what a reader sees. Without sorting, two-column pages come out interleaved and clauses break apart. Rejected: pdfplumber (slower on a 1144-page file), pypdf (weaker layout handling), and raw `get_text()` without sorting.

## D-007 · 2026-10-14 · Page text is stored raw, cleaning comes later
`pages.jsonl` holds each page's text exactly as PyMuPDF returns it: running headers, footers, page numbers and odd spacing included. Why: extraction and cleaning are separate steps, so a cleaning bug can be fixed and re-run without re-reading every PDF, and we can always compare the cleaned text against the original. The extract report only *lists* repeated header and footer lines so we can see what to strip next. Rejected: stripping headers during extraction, which hides what was removed and makes the output hard to check.

## D-008 · 2026-10-14 · The likely_scanned rule
A page is flagged `likely_scanned` when it has under 50 characters of text and at least one image, or under 20 characters in total. Why: a scanned page is a picture of text, so it reads as an image with almost no characters. The second half of the rule catches blank and image-free empty pages too. The thresholds are deliberately low so a sparse but real page (a section divider, a page with one heading) is not flagged. This is a flag for a human to look at, not a decision: nothing is dropped. It found all six DDA explainers to be fully scanned, which is what we needed to know. Rejected: comparing image area to page area (more code, no better answer at this stage) and running OCR right away (a separate decision, once we know how much text is missing).

## D-009 · 2026-10-14 · JSONL for page records
One JSON object per line in `data/processed/pages.jsonl`. Why: it appends and streams line by line, so a 944-page file never has to be held in memory at once, every record carries its own field names, and `git diff` on a generated file stays readable. Page text holds newlines, quotes and Hindi, all of which JSON escapes safely. Rejected: CSV (multi-line text in cells is fragile), one file per page (thousands of small files), and Parquet (an extra dependency for no gain at this size).

## D-010 · 2026-10-14 · The gazette's English part is selected by page range, not by editing the PDF
`MPD47_GAZETTE_EN.pdf` is the bilingual gazette: Hindi runs to page 639 and the English notification starts on page 640. `data/sources.csv` now has `page_start` and `page_end` columns (1-based, inclusive; blank means first page / last page), and the gazette is set to `page_start = 640`. Extraction reads only pages inside the range and keeps the original PDF page numbers. Why: a hand-split PDF is not reproducible (nobody can tell later which pages were cut, or re-do it after a re-download), and a citation has to point at the page number a reader will find in the official file. Rejected: splitting the PDF by hand, and renumbering the extracted pages from 1.

## D-011 · 2026-10-14 · Thresholds for the two report-only flags
A page counts as mostly Hindi when more than 30% of its non-space characters are in the Devanagari Unicode block. A line counts as a repeated header or footer when it is among the first two or last two non-empty lines on more than 40% of a document's pages. Why: both are warnings for a human reading the report, so loose thresholds are fine. Two notes from the first run, for the cleaning step: the gazette's running header carries the page number inside it, so no header line repeats literally and the 40% rule finds nothing for that document — matching will have to ignore digits. And the 8 "mostly Hindi" pages in the gazette's English range are sparse section dividers where the Hindi running header is most of the text on the page, not Hindi content. Rejected: counting Devanagari against all characters including spaces (whitespace-heavy pages would read as less Hindi than they are).

## D-012 · 2026-10-14 · Index the gazette only, and keep the chapter map beside it
We index `MPD47_GAZETTE_EN` English pages 640-1144 and drop `MPD47_PUBLICATION_EN` from the index. Why: `scripts/compare_plan_versions.py` showed they are the same plan text — 98% of sampled Publication sentences appear word for word in the gazette, 100% once punctuation is ignored, all 13 chapter headings and every numbered section line up, and no body heading is unique to the Publication — so indexing both would double-count every clause in retrieval. The gazette is the better copy of the two: it also carries pages 993-1144, the nine per-agency service plans (DJB, I&FCD, Delhi Cantonment Board, MCD, NDMC, DPCC, DTL, IGL and the IT department), which the Publication leaves out, and it loses no pages to images where the Publication loses 31 (13 empty, 18 image-only). The gazette's one defect, the bilingual running header on every page, is a single line per page for the cleaning step to drop. Rejected: indexing the Publication instead (missing the service plans and 31 pages of text), and indexing both with a de-duplication step at query time (more code, and the clause text is identical anyway).

`scripts/build_chapter_map.py` writes `data/chapter_map.json`: 19 entries, each with a chapter number or a section label, a title, and the gazette page range it covers. Why keep it: nothing in a page's own text says which chapter the page belongs to, so a citation cannot name the chapter without this map. Every title comes from the gazette's own heading page, written in title case, including the second and third lines that chapters 7 to 12 carry — so chapter 7 reads "Development Control Norms (DCN) for Residential" rather than the bare "DEVELOPMENT CONTROL NORMS (DCN)" that matching one line returns. Rejected: taking the chapter names from the Publication's contents list, which is what the first version of this file did. The gazette's wording is the text we actually index, it is more precise (chapter 12 is "Public and Semi-Public (PSP) – Social Infrastructure", not just "Public & Semi-Public"), and it carries no typo (the Publication's contents list reads "Transportation, Utilities and, Government"). Reading the titles from the gazette also means the map can be rebuilt after the Publication leaves `pages.jsonl`. The file is committed because it is small and hand-checked.

The map holds six labelled sections as well as the 13 numbered chapters: `Preamble` (640), the S.O. notification and the plan's opening paragraphs that come before chapter 1, then `abbreviations` (900), `definitions` (904), `annexures` (917), `maps` (987) and `service_plans` (993), each of which has a divider page of its own in the gazette. Why: every page from 640 to 1144 then sits in exactly one entry, and the script checks for gaps and overlaps on each run. Without the back-matter sections, chapter 13 would run from 884 to 992 and 93 pages of back matter — including Annexure 21, Use Premises and Permissible Activities, which is exactly the zoning content ZoneWise needs — would be cited as "Chapter 13: Other Controls". Rejected: 14 entries covering the chapters and the service plans only, which is how the step was first specified. One wrinkle for whoever reads the file: the labels are lower case with underscores, except `Preamble`, which was asked for with a capital.

## D-013 · 2026-10-15 · Chapter map labels are all lower case
Every non-numbered entry in `data/chapter_map.json` is lower case with underscores: `preamble`, `abbreviations`, `definitions`, `annexures`, `maps`, `service_plans`. Why: `Preamble` was the one capitalised label, which meant any code matching a label had to remember the exception. The label is an identifier used in code and in chunk metadata, not a display string — the entry's `title` field ("Notification preamble") is what a reader sees. Rejected: capitalising all six labels, which would push the same special case into the chunk metadata instead.

## D-014 · 2026-10-15 · reports/ is committed, data/layers/dda/ is not
Two new folders. `reports/` holds reports written for a human to read after a long run (`overnight_run.md`, `day2_queries.md`, `day3_location_compare.md`); it is committed because those reports are the record of what the run did and are small text. `data/layers/dda/` holds the GeoJSON downloaded from `gis.dda.org.in`; it is gitignored. Why gitignore the layers: the DDA FeatureServer states no licence or terms of use anywhere we could find, so we do not know that we may redistribute the data. Not committing it costs nothing — `scripts/06_fetch_layers.py` re-downloads it — and `data/layers/manifest.json` is committed so the repo still records exactly which layers were fetched, when, how many features each had and what fields they carry. Rejected: committing the layers (unknown redistribution rights), and keeping them outside `data/` (then nothing in the repo says where they belong).

## D-015 · 2026-10-15 · Day 2 dependencies, model cache and Chroma telemetry
Added with `uv add`: `fastembed` 0.9.0, `chromadb` 1.5.9, `rank-bm25` 0.2.2, `geopandas` 1.2.0, `shapely` 2.2.0, `pyproj` 3.8.0, `requests` 2.34.2. All seven installed on Windows first try, no version pinning needed. Two settings go with them. The fastembed model cache is `data/index/models`, inside the gitignored index folder: the BGE model is about 130 MB of downloaded weights, it is a build artefact like the index itself, and keeping it under `data/index/` means one folder to delete for a clean rebuild instead of hunting through a user-level cache. Chroma is created with `anonymized_telemetry=False`: a student project reading planning law has no reason to phone home, and the default sends usage events on import. Rejected: the default cache under `~/.cache/huggingface` (invisible to the project, and a second place to clean), and leaving telemetry on.
