# Decisions log
Each entry: what we decided, why, and what we rejected.

## D-001 · 2026-10-14 · Standalone repo
ZoneWise lives in its own repo, separate from the TerraTime capstone. Why: keeps the resume project clean. TerraTime can call ZoneWise's API later instead of merging code. Rejected: building inside the TerraTime repo.

## D-002 · 2026-10-14 · Python + FastAPI backend, React frontend, no MERN
Why: all the AI and map libraries we need are Python. There is nothing to store in MongoDB (no users; vectors live in Chroma), and Express would only add an extra hop. Rejected: MERN.

## D-003 · 2026-10-14 · No RAG frameworks
We write chunking, hybrid search, fusion and citation checks ourselves. Why: every step stays visible and explainable, and the codebase stays small. Rejected: LangChain, LlamaIndex.

## D-004 · 2026-10-14 · Documents downloaded by hand
Source PDFs are downloaded manually and listed in data/sources.csv with URL and download date. Why: government sites are slow and change often, there are only about 12 files, and the CSV keeps the work reproducible. Rejected: scraping scripts.

## D-005 · 2026-10-14 · Python 3.12 via uv
Why: one tool manages the Python version and the dependencies, with the same commands on Windows, Mac and Linux. Rejected: system Python + pip + venv.

## D-006 · 2026-10-14 · PyMuPDF for text, read in sorted order
We read page text with PyMuPDF's `page.get_text("text", sort=True)`. Why: PyMuPDF is fast (about 940 pages in under two minutes, including table detection) and `sort=True` returns the text blocks top-to-bottom and left-to-right instead of in the order the PDF happens to store them, which is what a reader sees. Without sorting, two-column pages come out interleaved and clauses break apart. Rejected: pdfplumber (slower on a 1144-page file), pypdf (weaker layout handling), and raw `get_text()` without sorting.

## D-007 · 2026-10-14 · Page text is stored raw, cleaning comes later
`pages.jsonl` holds each page's text exactly as PyMuPDF returns it: running headers, footers, page numbers and odd spacing included. Why: extraction and cleaning are separate steps, so a cleaning bug can be fixed and re-run without re-reading every PDF, and we can always compare the cleaned text against the original. The extract report only *lists* repeated header and footer lines so we can see what to strip next. Rejected: stripping headers during extraction, which hides what was removed and makes the output hard to check.

## D-008 · 2026-10-14 · The likely_scanned rule
A page is flagged `likely_scanned` when it has under 50 characters of text and at least one image, or under 20 characters in total. Why: a scanned page is a picture of text, so it reads as an image with almost no characters. The second half of the rule catches blank and image-free empty pages too. The thresholds are deliberately low so a sparse but real page (a section divider, a page with one heading) is not flagged. This is a flag for a human to look at, not a decision: nothing is dropped. It found all six DDA explainers to be fully scanned, which is what we needed to know. Rejected: comparing image area to page area (more code, no better answer at this stage) and running OCR right away (a separate decision, once we know how much text is missing).

## D-009 · 2026-10-14 · JSONL for page records
One JSON object per line in `data/processed/pages.jsonl`. Why: it appends and streams line by line, so a 944-page file never has to be held in memory at once, every record carries its own field names, and `git diff` on a generated file stays readable. Page text holds newlines, quotes and Hindi, all of which JSON escapes safely. Rejected: CSV (multi-line text in cells is fragile), one file per page (thousands of small files), and Parquet (an extra dependency for no gain at this size).

## D-010 · 2026-10-14 · The gazette's English part is selected by page range, not by editing the PDF
`MPD47_GAZETTE_EN.pdf` is the bilingual gazette: Hindi runs to page 639 and the English notification starts on page 640. `data/sources.csv` now has `page_start` and `page_end` columns (1-based, inclusive; blank means first page / last page), and the gazette is set to `page_start = 640`. Extraction reads only pages inside the range and keeps the original PDF page numbers. Why: a hand-split PDF is not reproducible (nobody can tell later which pages were cut, or re-do it after a re-download), and a citation has to point at the page number a reader will find in the official file. Rejected: splitting the PDF by hand, and renumbering the extracted pages from 1.

## D-011 · 2026-10-14 · Thresholds for the two report-only flags
A page counts as mostly Hindi when more than 30% of its non-space characters are in the Devanagari Unicode block. A line counts as a repeated header or footer when it is among the first two or last two non-empty lines on more than 40% of a document's pages. Why: both are warnings for a human reading the report, so loose thresholds are fine. Two notes from the first run, for the cleaning step: the gazette's running header carries the page number inside it, so no header line repeats literally and the 40% rule finds nothing for that document — matching will have to ignore digits. And the 8 "mostly Hindi" pages in the gazette's English range are sparse section dividers where the Hindi running header is most of the text on the page, not Hindi content. Rejected: counting Devanagari against all characters including spaces (whitespace-heavy pages would read as less Hindi than they are).

## D-012 · 2026-10-14 · Index the gazette only, and keep the chapter map beside it
We index `MPD47_GAZETTE_EN` English pages 640-1144 and drop `MPD47_PUBLICATION_EN` from the index. Why: `scripts/compare_plan_versions.py` showed they are the same plan text — 98% of sampled Publication sentences appear word for word in the gazette, 100% once punctuation is ignored, all 13 chapter headings and every numbered section line up, and no body heading is unique to the Publication — so indexing both would double-count every clause in retrieval. The gazette is the better copy of the two: it also carries pages 993-1144, the nine per-agency service plans (DJB, I&FCD, Delhi Cantonment Board, MCD, NDMC, DPCC, DTL, IGL and the IT department), which the Publication leaves out, and it loses no pages to images where the Publication loses 31 (13 empty, 18 image-only). The gazette's one defect, the bilingual running header on every page, is a single line per page for the cleaning step to drop. Rejected: indexing the Publication instead (missing the service plans and 31 pages of text), and indexing both with a de-duplication step at query time (more code, and the clause text is identical anyway).

`scripts/build_chapter_map.py` writes `data/chapter_map.json`: 19 entries, each with a chapter number or a section label, a title, and the gazette page range it covers. Why keep it: nothing in a page's own text says which chapter the page belongs to, so a citation cannot name the chapter without this map. Every title comes from the gazette's own heading page, written in title case, including the second and third lines that chapters 7 to 12 carry — so chapter 7 reads "Development Control Norms (DCN) for Residential" rather than the bare "DEVELOPMENT CONTROL NORMS (DCN)" that matching one line returns. Rejected: taking the chapter names from the Publication's contents list, which is what the first version of this file did. The gazette's wording is the text we actually index, it is more precise (chapter 12 is "Public and Semi-Public (PSP) – Social Infrastructure", not just "Public & Semi-Public"), and it carries no typo (the Publication's contents list reads "Transportation, Utilities and, Government"). Reading the titles from the gazette also means the map can be rebuilt after the Publication leaves `pages.jsonl`. The file is committed because it is small and hand-checked.

The map holds six labelled sections as well as the 13 numbered chapters: `Preamble` (640), the S.O. notification and the plan's opening paragraphs that come before chapter 1, then `abbreviations` (900), `definitions` (904), `annexures` (917), `maps` (987) and `service_plans` (993), each of which has a divider page of its own in the gazette. Why: every page from 640 to 1144 then sits in exactly one entry, and the script checks for gaps and overlaps on each run. Without the back-matter sections, chapter 13 would run from 884 to 992 and 93 pages of back matter — including Annexure 21, Use Premises and Permissible Activities, which is exactly the zoning content ZoneWise needs — would be cited as "Chapter 13: Other Controls". Rejected: 14 entries covering the chapters and the service plans only, which is how the step was first specified. One wrinkle for whoever reads the file: the labels are lower case with underscores, except `Preamble`, which was asked for with a capital.

## D-013 · 2026-10-15 · Chapter map labels are all lower case
Every non-numbered entry in `data/chapter_map.json` is lower case with underscores: `preamble`, `abbreviations`, `definitions`, `annexures`, `maps`, `service_plans`. Why: `Preamble` was the one capitalised label, which meant any code matching a label had to remember the exception. The label is an identifier used in code and in chunk metadata, not a display string — the entry's `title` field ("Notification preamble") is what a reader sees. Rejected: capitalising all six labels, which would push the same special case into the chunk metadata instead.

## D-014 · 2026-10-15 · reports/ is committed, data/layers/dda/ is not
Two new folders. `reports/` holds reports written for a human to read after a long run (`overnight_run.md`, `day2_queries.md`, `day3_location_compare.md`); it is committed because those reports are the record of what the run did and are small text. `data/layers/dda/` holds the GeoJSON downloaded from `gis.dda.org.in`; it is gitignored. Why gitignore the layers: the DDA FeatureServer states no licence or terms of use anywhere we could find, so we do not know that we may redistribute the data. Not committing it costs nothing — `scripts/06_fetch_layers.py` re-downloads it — and `data/layers/manifest.json` is committed so the repo still records exactly which layers were fetched, when, how many features each had and what fields they carry. Rejected: committing the layers (unknown redistribution rights), and keeping them outside `data/` (then nothing in the repo says where they belong).

## D-015 · 2026-10-15 · Day 2 dependencies, model cache and Chroma telemetry
Added with `uv add`: `fastembed` 0.9.0, `chromadb` 1.5.9, `rank-bm25` 0.2.2, `geopandas` 1.2.0, `shapely` 2.2.0, `pyproj` 3.8.0, `requests` 2.34.2. All seven installed on Windows first try, no version pinning needed. Two settings go with them. The fastembed model cache is `data/index/models`, inside the gitignored index folder: the BGE model is about 130 MB of downloaded weights, it is a build artefact like the index itself, and keeping it under `data/index/` means one folder to delete for a clean rebuild instead of hunting through a user-level cache. Chroma is created with `anonymized_telemetry=False`: a student project reading planning law has no reason to phone home, and the default sends usage events on import. Rejected: the default cache under `~/.cache/huggingface` (invisible to the project, and a second place to clean), and leaving telemetry on.

## D-016 · 2026-10-15 · Cleaning rules, applied per page before chunking
`app/cleaning.py` strips six things from every page and keeps everything else. (1) The gazette's running header, matched on its wording rather than its exact text, because the page number sits inside the line ("750 THE GAZETTE OF INDIA : EXTRAORDINARY [PART II—SEC. 3(ii)]") so no two copies are identical — see D-011. Both the English and the Hindi form are matched. (2) Lines that are only a page number. (3) Figure and map captions ("Illustration 6: Transit Oriented Development (TOD)", "(For illustrative purpose only)"): the picture is not in the index, so a caption on its own is a retrievable line that answers nothing. (4) Divider lines ("CHAPTER 4. SPATIAL DEVELOPMENT POLICIES", "PART I: BACKGROUND"), because data/chapter_map.json already says which chapter a page is in and the line would otherwise become a two-word chunk. (5) Inside the gazette's English range, any remaining line that is more than 30% Devanagari — the eight such pages are section dividers where the Hindi header is most of the page. (6) Runs of spaces inside a line, which justified text leaves behind ("Kartavya  Path  development"). Line breaks are kept at this stage because heading and sub-item detection needs them; the chunker joins wrapped lines into paragraphs afterwards. Each kept line carries the page it was printed on, so a chunk that crosses a page break reports an honest page_start and page_end. Rejected: dropping the headers during extraction (D-007 keeps extraction and cleaning separate), and matching the header by exact string (it never repeats exactly).

The FAQ, the court order and the NGT report each carry a different running header, so for those three the 40% repeated-edge-line rule from the extract step is reused, comparing lines with their digits removed. That is what catches "Indian Kanoon - http://indiankanoon.org/doc/28108780/ 3", whose trailing page number makes every copy unique. Rejected: hard-coding the three headers, which would break on the next document added.

## D-017 · 2026-10-15 · A word broken across a line end keeps its hyphen
"compact mixed-" at the end of one line and "use development" at the start of the next is joined into "mixed-use development": the two halves are joined and the hyphen is kept. Why: we cannot tell a compound word that happened to wrap ("mixed-use", "transit-oriented") from a word the typesetter hyphenated to fit the line ("develop-ment"), and in this gazette the wrapped ones are compounds — spot-checked across chapters 4, 7 and 13. Keeping the hyphen leaves a real compound intact; dropping it would silently rewrite "mixed-use" as "mixeduse" and break both the keyword index and the quoted text. The join only fires when the next line starts with a lower-case letter, so a hyphen at the end of a heading or a list item is left alone. Rejected: dropping the hyphen, and leaving both halves on separate lines, which would split "mixed-use" into two tokens in the BM25 index.

## D-018 · 2026-10-15 · Tables become markdown, with a plain-text fallback per page
On a page where PyMuPDF finds tables, each table is read with `table.extract()` and written as a markdown table, and the text around it is read with `get_text(clip=...)` over the horizontal bands the tables leave free, so no sentence is in the chunk twice. The tables go back in reading order, top to bottom. Why markdown: it is the format the model reads best, it survives in a JSONL string, and a row keeps its columns together, which a flat text dump does not — the development control norms in chapters 7 to 12 are almost all tables, so losing their shape would lose the plan's actual numbers. 289 of 331 tables in the gazette converted.

A table is rejected when more than half its cells are empty or it has fewer than two columns, and then the whole page falls back to plain text and the run logs a warning. 42 tables fell back, all but five of them in the service plans' drainage and waste tables, which are sparse engineering sheets that PyMuPDF reads as a grid of blanks. The fallback is per page, not per table, because the clipping bands are computed from all of the page's tables at once; mixing a converted table with a plain-text read of the same page would duplicate text. A table chunk that runs over the size limit is split by groups of rows with the header row repeated on each piece, so a piece retrieved on its own still says what its columns mean. Rejected: keeping a garbled table (it reads as rows of empty pipes and would pollute the index), dropping the page entirely (the text around the table is fine), and pdfplumber's table extraction (a second PDF library for one job — D-006).

## D-019 · 2026-10-15 · The section heading regex, checked against the chapter number
A gazette section heading is a line of the form N.N, N.N.N or N.N.N.N, then a title that starts with a capital letter and is at most 120 characters: "4.2 TRANSIT ORIENTED DEVELOPMENT (TOD)", "4.2.1 Definitions". The pattern alone is not enough — a table cell reads as "3.50 80.50 0.05" and a measurement reads as "2.0 Ha" — so inside chapters 1 to 13 the first number must equal the chapter number the page belongs to, from data/chapter_map.json. That single check removes every false positive in 250 pages of norms tables: a stray "3.5" in chapter 11 cannot be a heading, and a real "11.1" can.

The service plans (pages 993-1144) have no chapter number to check against, because each of the nine agency documents numbers its own sections from 1. Three cheaper guards stand in: no part of the number may be above 20, the number may be at most three levels deep, and the title must be at least four characters. Together those reject the drainage tables' measurements ("5.90 Good NO NO RD-5900m to RD-0m", "19.7 RD") while keeping the real headings ("3.3 DETAILS OF MANAGEMENT OF PLASTIC WASTE", "4.4 Timelines:"). The agency headings themselves ("1. SERVICE PLAN – DELHI JAL BOARD (DJB)") are matched case-sensitively on purpose: the contents page on gazette page 994 lists the same nine plans in title case, and those lines are a table of contents, not the start of a plan. Rejected: requiring a heading to be followed by body text (two passes over the stream for little gain), and tracking whether each number continues the sequence (more state, and the three guards already catch everything in this document).

## D-020 · 2026-10-15 · Chunk sizes: 150-400 words, merge under 40, split over 500
A chunk aims at 150 to 400 words. Under about 150 a chunk is usually half a thought and the embedding has little to work with; over about 400 it starts to cover two subjects and the citation stops being precise. Three rules get there, and each is recorded in the chunk report so the shape of the result is visible: a section under 40 words is merged with its next sibling under the same parent while the result stays at or under 500, and both clause numbers are kept in clause_ids; a section over 500 words is split at sub-item boundaries ("(i)", "(a)"), then at paragraph boundaries; and a single paragraph over 650 words, which has no seam to cut on, is split by sentences with about 40 words repeated from the piece before it. The result: 702 chunks, 64% in the 150-400 band, none over 500 words.

Two rules were added because the specified ones left useless chunks behind. A heading with no text of its own ("11.1 Transportation", sitting alone above 11.1.1 and 11.1.2) is folded into its first child rather than merged with a sibling, because its child is not its sibling and the sibling rule could not reach it — that alone was 36 two-word chunks. Folding has no size limit, unlike the sibling merge: a heading belongs to the text beneath it, so folding cannot glue two unrelated clauses together, and the result goes through the splitting rules straight afterwards. Separately, a split can leave a scrap at the end ("(ii) The above activities shall be subject to clearances from ..." on its own is 12 words), so a piece under 40 words is put back on the piece before it where there is room; both pieces came from one section, so nothing is mixed up. Rejected: dropping short chunks (a real one-line clause would go with them) and raising the merge threshold (it would start joining unrelated clauses).

The 56 chunks still under 40 words are honest: 45 are FAQ answers that really are one line, where the specification asks for one chunk per question, and the rest are annexure titles whose body is a table that was split off, and cover-page fragments of the NGT report.

## D-021 · 2026-10-15 · Chunk ids, and what makes them unique
A chunk id reads `<doc_id>:<clause id>:<piece number>`, for example `MPD47_GAZETTE_EN:4.2.1:0`. The piece number counts the pieces a section was split into, so re-running the pipeline on the same input gives the same ids and nothing downstream has to be rebuilt. A chunk with no clause number uses its first page instead: `MPD47_GAZETTE_EN:p988:0`.

Clause numbers are not unique in this corpus, which the first version of the format missed. The FAQ restarts at Q1 in each of its nine sections; the nine service plans each number their sections from 1.1, and those numbers also collide with chapters 1 to 13 of the plan proper, which sit in the same doc_id. So any id that would repeat gets its page appended — `MPD47_FAQ:Q12@p16:0`, `MPD47_GAZETTE_EN:3.1@p677:0` — and a `+` suffix after that, which nothing in this corpus needs. All 702 ids are distinct. Rejected: a hash of the text (nothing in the id would tell a reader where the chunk came from, and the id would change whenever the cleaning rules change) and a plain running number (it moves when a chunk is added upstream).

## D-022 · 2026-10-15 · embed_text carries a one-line breadcrumb above the text
What goes to the embedding model is not the chunk text alone but one header line and then the text. For the gazette the header is `MPD-2047 > <chapter title> > <heading path>` (written with the > character), for example "MPD-2047 > Spatial Development Policies > 4.2 TRANSIT ORIENTED DEVELOPMENT (TOD) > 4.2.1 Definitions"; for the other three documents it is the document title. Why: a clause often does not name its own subject — 4.2.1 says "area under 500m wide corridor on either side of centreline" and never the words "transit oriented development" in the sentence a user would match on — so without the breadcrumb a question about TOD cannot reach it. text stays clean and is what gets shown and quoted; embed_text is only ever fed to the index. Rejected: embedding the bare text (loses the context the heading carries), and repeating the full heading path inside text (the display would read awkwardly and the quote would not match the gazette).

## D-023 · 2026-10-15 · Two kinds of zone tag: primary may exclude, a mention may only boost
Each chunk gets `zone_primary` (one topic, or empty) and `zone_mentions` (a list), plus eight flat booleans so the search index can filter on scalars: `zp_tod`, `zp_hdc`, `zp_zone_o`, `zp_land_pooling` for the primary zone and `zm_*` for mentioned-or-primary.

`zone_primary` comes from the heading path, never from the words. A chunk is tagged tod only if it sits under section 4.2, hdc only under 4.3, land_pooling only under 4.1 — the mapping lives in `data/zone_sections.json`, which is committed. That makes it a strong claim: a chunk with `zone_primary = "tod"` is a rule that holds inside the TOD zone and nowhere else, which is why search is allowed to drop it for a point that is not in a TOD zone.

`zone_mentions` comes from the text and is a weak claim, used only to rank a chunk higher. It has to be weak: section 4.6.1 names Zone O in the list of areas it does *not* apply to, and 11.1.1 says fuel stations are permitted "in all Use Zones except ... Zone O". A chunk that mentions a zone to exclude it is still the chunk a user standing in that zone needs, so a mention must never cause a drop. 181 of 702 chunks (26%) carry at least one tag; 24 carry a primary zone.

Only the plan's numbered chapters are considered for `zone_primary`. The nine service plans at the back of the gazette number their own sections from 1.1 in the same `doc_id`, so a Delhi Jal Board sewerage section numbered 4.2 would otherwise be read as the TOD policy. Rejected: deciding the primary zone from the text (every mention would become a rule, and the exclusion step would then drop the very clauses that list a zone as an exception), and one combined tag (there would be no way to say "boost but never drop").

## D-024 · 2026-10-15 · zone_o has no policy section of its own, and that is the finding
`data/zone_sections.json` maps `zone_o` to an empty list. MPD-2047 has no Zone O policy. Section 1.7.2 defines planning zone O as "River Yamuna / Riverfront", one of the 17 planning zones, and from there the plan names it only inside other policies' exclusion lists: "shall not apply to ... Zone 'O'" in 4.2.2, 4.5.1 and 4.6.1, and "all Use Zones except Recreational ... and Zone O" in 11.1.1, which is the clause that answers "can a fuel station be built in Zone O?".

The nearest candidate was 3.1.2 Green-Blue Infrastructure, which carries the real floodplain rule ("Active floodplain shall be a 'no construction zone' and only recreational uses shall be permitted"). It was rejected because that section is about every green and blue asset in Delhi — parks, drains, water-body buffers, eco-cultural assets — not about Zone O. Naming it as Zone O's own policy would let the exclusion step drop it for any point outside the floodplain, and a question about a water-body buffer at an ordinary address would lose its answer. So Zone O works through mentions alone: it can boost a result and expand a query, and it can never lose a chunk. 53 chunks mention it, including 20 of the 47 NGT report chunks and 2 of the 8 High Court order chunks, which are the documents that actually regulate the floodplain.

This is the one place tonight where the specification asked for something the document does not contain, so it is flagged for review: if Zone O should be able to exclude, 3.1.2 is the section to add, and the trade-off above is the reason not to.

## D-025 · 2026-10-15 · The zone mention regexes are case-aware, and the false positives are tested
Matching is by word boundary, and case matters where the short form is also an ordinary word.

- tod: `\bTOD\b` in capitals only, and `transit[- ]oriented development` either case.
- hdc: `high[- ]density corridor`, `\bHDC\b` in capitals, `\bUER[- ]?II\b` (so both "UER-II" and "UER II"), `urban extension road`.
- zone_o: `\bZone\s*['"]?O\b` — capital Z, a standalone capital O, with optional quotes because the gazette writes Zone 'O' — plus `Zone O-1`, `Zone O-2` and `Yamuna flood ?plain`.
- land_pooling: `land pooling`, `pooled land`.

The capital-O-as-a-whole-word rule is what makes "zone of", "Zone of the river" and "TOD Zone or" fail to match while "Zone O", "Zone 'O'", "Zone O-1" and "Zone O Lutyens" match. "TOD Zone or" is tagged tod and nothing else; "flood plain zone of river" is tagged nothing at all. Both are in `tests/test_tagging.py`.

One condition is kept separate from the phrase list: a chunk also counts as zone_o when it names "river Yamuna" *and* uses the word "flood" somewhere, which is how the court order and the NGT report talk about the floodplain without ever writing "Zone O". It is two conditions rather than one phrase precisely so that "flood plain zone of river", which has neither "Yamuna" nor a capital-O zone, stays untagged. Rejected: matching "flood plain" on its own (it appears in drainage and disaster sections that have nothing to do with Zone O), and case-insensitive `\btod\b` (it fires inside no English word, but "TOD" in lower case appears in URLs and file names in the source documents).

## D-026 · 2026-10-15 · Chroma holds scalar metadata only, and is rebuilt through the client
The dense index is a persistent Chroma collection named `chunks` at `data/index/chroma`, built with cosine distance (`configuration={"hnsw": {"space": "cosine"}}`) and `embedding_function=None`, because ZoneWise embeds its own text with fastembed and hands Chroma the vectors. Cosine rather than L2: BGE embeddings are meant to be compared by angle, and cosine is scale-free, so a long chunk is not penalised for having a longer vector.

Each vector carries only scalar metadata — `doc_id`, `doc_type`, `authority_rank`, `chapter`, `clause_id`, `page_start`, `page_end`, `has_table`, `zone_primary` and the eight zone booleans. Chroma takes strings, numbers and booleans and nothing else, so `clause_id` is stored as `""` rather than null, and the three list fields (`heading_path`, `clause_ids`, `zone_mentions`) are left out and read back from `chunks.jsonl` at search time. That also keeps `chunks.jsonl` the single source of truth for chunk text: the index stores what it needs to filter and rank, not what it needs to display. The eight booleans are flattened precisely because a list cannot be filtered on: `zm_tod = true` is a `where` clause, `zone_mentions contains "tod"` is not.

To rebuild, the collection is deleted and recreated **through the client**, never by removing the folder. On Windows the SQLite file underneath is locked while the client is open, so deleting the directory from under it either fails outright or leaves a half-written store that the next run reads as valid. Rejected: deleting `data/index/chroma` at the start of the build (the Windows lock), and upserting over the old collection (a chunk whose id disappeared upstream would survive forever).

## D-027 · 2026-10-15 · The keyword tokenizer keeps clause numbers whole
BM25 runs over the same `embed_text` as the embeddings, tokenised as: lower case, runs of `[a-z0-9]`, and a dotted number kept as one token when every part of it is digits. So "4.2.1" stays "4.2.1" and a search for that clause number finds that clause, instead of matching every chunk that contains a 4, a 2 and a 1. Anything else that picked up a dot is split on the dot, because "policy.The" at a sentence join is two words. Hyphens split, so "mixed-use" indexes as "mixed" and "use" and a query written either way matches.

Stopwords are a 120-word English list written out in `app/indexing.py` rather than taken from NLTK or scikit-learn, because one list of common words is not worth a dependency (and CLAUDE.md asks before adding one). 702 documents, 11,126 distinct tokens.

The BM25 model is pickled to `data/index/bm25.pkl` **together with the list of chunk ids in corpus order**. That is not optional: `BM25Okapi.get_scores` returns an array indexed by corpus position, so a score array is meaningless without the list that says which chunk each slot belongs to. Rejected: rebuilding BM25 on every search (0.2 s to build but it has to read all 702 chunks first), and storing the keyword index in Chroma's full-text search (it would tie the keyword side to Chroma's tokenizer, which we cannot see or test).

## D-028 · 2026-10-15 · Both pools are 30 deep, fused with RRF at k = 60
Dense and keyword each return their top 30, and hybrid fuses the two lists with reciprocal rank fusion: a chunk's score is the sum of `1 / (60 + rank)` over the lists it appears in, ranks counted from 1.

Fusion uses ranks and never scores, which is the whole reason it is safe here. A cosine distance runs 0 to 2 and a BM25 score runs 0 to about 30 and depends on the corpus; adding or averaging them would let BM25 decide every hybrid result. Rank orders have no units and can be combined.

k = 60 is the value from the paper RRF comes from, and it behaves the way this corpus needs: with k = 60 rank 1 scores 0.0164 and rank 2 scores 0.0161, a 2% gap, so a chunk that both indexes place in their top ten beats a chunk that one index ranked first and the other missed entirely. Agreement counts for more than one index's confidence. A small k (say 1) would do the opposite — rank 1 would score twice rank 2 — and the fusion would mostly echo whichever index was more certain. Pool depth 30 is five times the default k of 6, which leaves room for fusion to reorder without pulling in chunks neither index thought much of.

One detail that is a decision rather than a default: a BM25 result scoring exactly zero shares no token with the query, so it is dropped from the pool instead of padding it out to 30. Without that, an unrelated chunk sitting at keyword rank 12 would still earn fusion points and could outrank a genuine dense-only match. Rejected: normalising the two score scales and adding them (the normalisation would have to be refitted whenever the corpus changes), and a fixed weight per index (nothing in the data says what the weight should be).

## D-029 · 2026-10-15 · passage_embed for chunks, query_embed for questions
The dense index is built with fastembed's `passage_embed` and searched with `query_embed`. BGE models are trained with an asymmetric objective: the query side gets a short instruction prefix ("Represent this sentence for searching relevant passages:") and the document side gets none. Using the same call for both costs real accuracy on short questions, which is exactly what ZoneWise is asked. The model is `BAAI/bge-small-en-v1.5`, 384 dimensions, and its weights are cached in `data/index/models` (D-015). Embedding all 702 chunks takes about 140 seconds on this laptop's CPU, around 5 chunks a second; a single query embeds in well under a tenth of a second. Rejected: `embed()` for both sides, and a larger BGE model (base is three times the size for a gain that would not show on a corpus this small).

## D-031 · 2026-10-15 · get_zones: STRtree per layer, `covers` not `contains`, loaded once
`app/spatial.py` loads each layer's polygons into a shapely `STRtree` and caches the lot with `lru_cache`, because the point-in-polygon work is trivial but parsing 4.8 MB of GeoJSON on every query is not. A query narrows by bounding box through the tree and then tests the candidates exactly.

The exact test is `covers`, not `contains`. `contains` is false for a point sitting precisely on a polygon's boundary, and the planning zones tile Delhi with shared edges, so a point on a boundary would belong to no zone at all. `covers` includes the boundary, so such a point belongs to the first zone that claims it. The choice is recorded because it is the kind of thing that looks like a typo later.

A point outside NCT Delhi returns `{"inside_delhi": False}` and nothing else: "is this plot in a TOD zone?" has no honest answer for a point in Gurugram, and returning `tod: False` would read as "no, and we checked". Inside Delhi the answer carries `planning_zone`, the four policy flags, `land_pooling_zone` where the layer names one, and `regional_park` and `lda` for the two extra layers that are loaded but not yet used in retrieval. Rejected: GeoPandas `sjoin` per query (it builds a frame each time for a single point), and buffering the point (nothing in the brief asks "near", only "in").

## D-033 · 2026-10-15 · Location-aware search: exclude, expand, boost — in that order
`app/location.py` adds three steps to hybrid search when the caller passes a point's `get_zones` result, with every setting in `app/config.py` so they can be turned off one at a time.

**1. Exclusion.** A chunk whose `zone_primary` is one of the policies the point is *not* in is dropped. At P_PLAIN, in planning zone G and in none of the four policies, that removes 7 chunks — the TOD, HDC and land pooling policy sections — because those rules do not apply to that plot at all. A chunk with no primary zone is never dropped, which is the safety catch: the general development control norms in chapters 7 to 13 carry no primary zone, so they are always in play.

The filtering happens **before the ranks are read**, not after fusion. If a dropped chunk kept its rank slot, everything below it would lose fusion points for the presence of something that is not in the results. For the same reason the pools are fetched twice as deep as they are used (60 instead of 30) and then filtered down, so there is still a full pool to fuse after dropping.

**2. Query expansion.** The point's zone names and their short forms are appended to the query for both indexes: "transit oriented development TOD zone", "high density corridor HDC UER-II", "Zone O Yamuna floodplain", "land pooling". This is what makes a question with no zone words in it work at all. "What is the maximum ground coverage allowed on my plot?" contains nothing for either index to match on, so plain hybrid answers it from whichever ground-coverage clause is most popular — which turns out to be the TOD one, wherever the user is standing. Expansion gives the dense index the planner's phrasing and the keyword index the exact short forms the gazette prints.

**3. Boost.** A chunk whose `zone_primary` *or* `zone_mentions` matches one of the point's zones has its fused score multiplied by 1.5. Boosting is the weak step: it reads mentions as well as primary, so a chunk that merely names the zone can be lifted, but nothing is ever pushed out of the corpus by it.

Order matters: excluding first means the boost is applied to a pool that already has the wrong-zone rules out of it, so the 1.5 is spent lifting relevant chunks rather than fighting irrelevant ones.

A point outside NCT Delhi gets a plain search, all three steps off. Strictly, exclusion would drop all 24 primary-zone chunks for such a point, since it is in none of the four zones. That would be the wrong behaviour dressed up as the right one: MPD-2047 does not apply in Gurugram at all, so filtering its TOD sections there answers a question nobody asked. Saying "this point is not in Delhi" belongs to the answering step (Day 4), not to retrieval. Rejected: treating a point outside Delhi as a point in no zone.

## D-034 · 2026-10-15 · The boost is 1.5, and here is what that is worth
1.5 is the multiplier asked for in the brief, and it is worth writing down what it actually buys, because an RRF score is not intuitive. A chunk at rank 1 in both indexes scores 2/(60+1) = 0.0328. A boosted chunk at rank r in both indexes scores 1.5 × 2/(60+r), and the two are equal at r = 31.5. The pools are only 30 deep, so **within the pool, a boosted chunk that both indexes returned beats any unboosted chunk, wherever it sat.** That is stronger than it first sounds, and it is the reason the exclusion step matters: the boost is close to decisive, so it had better be applied to a pool that no longer contains the wrong zone's rules.

What the boost does *not* do is let one index overrule the other. A boosted chunk that only one index found, even at rank 1, scores 1.5 × 1/61 = 0.0246, which still loses to an unboosted chunk both indexes ranked first at 0.0328. So agreement between the two indexes survives the boost, and a chunk neither index rated cannot be dragged to the top by being in the right zone. Both of those arithmetic claims are asserted in `tests/test_retrieval.py` rather than left as prose.

The effect shows most clearly at P_HDC, where plain hybrid's top two results are the TOD ground coverage rules — the wrong policy for that plot — and location-aware search returns 4.3.3 HDC Norms first and second. At P_ZONEO, "Can I construct a building here?" goes from heritage-façade FAQs to 3.1.2's "Active floodplain shall be a 'no construction zone'" at rank 1, with the Delhi High Court order second. Those are in `reports/day3_location_compare.md` for judging by hand. Rejected: tuning the multiplier tonight — there is no labelled evaluation set yet, so any number past 1.5 would be fitted to four hand-read examples.

## D-040 · 2026-10-15 · One door to the model, a FakeLLM behind it, and a key check that rejects placeholders
`app/llm.py` now offers two methods — `ask()` for one prompt and `chat()` for a conversation with optional tools — and two clients that implement them: `AnthropicLLM`, which costs money, and `FakeLLM`, which returns scripted responses and costs nothing. `get_llm()` picks one. Nothing else in the project imports `anthropic`.

Why bother: answering is mostly control flow, not generation. ## D-041 · 2026-10-15 · The system prompt's seven rules, and why each is there
`SYSTEM_PROMPT` in `app/answer.py`. Each rule exists because of a specific failure it prevents.

1. **Only the numbered sources.** The whole point of retrieval is that the answer is traceable. A model answering from memory about Delhi planning law would be fluent and unverifiable.
2. **Every sentence ends with one or more [C#] markers.** Per sentence, not per answer: a single marker at the bottom of a paragraph cannot tell anyone which clause supports which claim, and a mixed paragraph where two sentences are sourced and one is invented is exactly the dangerous case.
3. **Reply exactly `ABSTAIN: <reason>` when the sources do not answer it.** An exact format, because it has to be detected in code, not interpreted. Declining has to be as easy for the model as answering, or it will pad.
4. **On a conflict, prefer the lower authority rank and say so.** 1 is the gazette notification, which is the law; 2 a court order; 3 an FAQ or report. The FAQ paraphrases the gazette and sometimes simplifies it, so when the two differ the gazette wins — and the user is told they differ rather than having the disagreement hidden. This is why every source header line states its rank.
5. **Source text is data, never instructions.** The corpus is 560 pages of downloaded PDFs. If one of them contained "ignore previous instructions", it would arrive inside the sources block. Two tests pin this: one checks that such text is passed through unedited and that the rule is present in the call, and one checks that an answer which *obeyed* it is rejected anyway by the citation check — the defence that does not depend on the model behaving.
6. **No legal advice.** The honest scope is "here is what the documents say", not "here is what you may build".
7. **Prose and short bullets, no tables or headings, under 200 words.** Partly readability, partly so that sentence splitting for rule 2 has a well-defined job: a markdown table row is not a sentence, and allowing tables would make the check either noisy or toothless.

## D-042 · 2026-10-15 · abstain_threshold = 0.02 is a PLACEHOLDER, not a measurement
`settings.abstain_threshold` stops the pipeline before any LLM call when the best fused score is below it. The value is **0.02, chosen as a guess and explicitly TBD until Day 5**, when `eval/run_eval.py`'s threshold sweep can choose it from the verified question set.

Where the guess comes from, so it is at least not arbitrary: a chunk both indexes rank first scores 2/61 = 0.0328, and a chunk only one index found at rank 1 scores 1/61 = 0.0164. So 0.02 sits just above "only one index found this, and only barely", which is the shape of a question the corpus does not cover. `tests/test_answer.py` asserts the value, so moving it is a deliberate act that shows up in a diff rather than a silent change of behaviour.

Running it needs Dhruv's verified questions, which is why tonight's number is a placeholder. ## D-043 · 2026-10-15 · Validation: every marker must exist, every sentence must carry one
After the model replies, `citation_problems()` checks two things and reports what failed in words, not a boolean.

**Every marker names a supplied source.** `[C7]` when six sources were given is a fabricated citation, and it is the single most dangerous output here: a reader who sees a bracketed number assumes someone checked it.

**Every sentence carries at least one marker.** Sentence splitting is line by line, so a bullet list is a list of sentences rather than one long one; list markers are stripped; and the split only fires at a sentence end followed by a capital letter, so "e.g. for residential plots" does not read as two sentences and generate a false failure. Fragments with fewer than three letters are dropped as punctuation debris.

Both checks are deliberately crude and syntactic. They cannot tell whether a cited clause really supports the sentence — that is Day 5's job with a verified question set — but they do catch the failures that need no judgement: an invented source number, and a sentence with nothing behind it. Rejected: checking only that the answer contains at least one citation somewhere (passes an answer where one sentence in four is invented), and asking a second model call to grade the first (another call, another thing to go wrong, and no ground truth).

## D-044 · 2026-10-15 · One retry, with the problems named, then abstain
A failed citation check gets exactly one retry. The retry is a real conversation turn: the model's own answer goes back as an assistant message, followed by a user message listing the specific problems ("[C9] does not refer to a source you were given"; "1 sentence(s) carry no citation marker at all. The first is: ...") and restating the valid marker range. Seeing its own text with the fault named is far more likely to produce a fix than re-sending the original prompt.

Why one and not three: the second failure is evidence that the model cannot ground this particular question from these particular sources, and more attempts cost money and latency for a shrinking chance. If the second attempt also fails, the answer is discarded and the result is an abstention with reason `citation_check_failed` — but the retrieved clauses are still returned, so the interface can show the user the clauses it found and let them read for themselves. An honest "I could not answer this, here are the relevant clauses" is a useful product; a sentence with no source behind it is not. Rejected: showing the failed answer with a warning (nobody reads the warning), and retrying forever.

## D-045 · 2026-10-15 · Four abstention reasons, two of which never call the model
`AnswerResult.abstain_reason` is one of four strings, and which one it is matters to the interface, so they are separate rather than one generic "cannot answer".

- `outside_delhi` — the point is not in NCT Delhi. No search, no LLM call. "Is this plot in a TOD zone?" has no honest answer in Gurugram, and MPD-2047 simply does not apply there.
- `weak_retrieval` — nothing came back, or the best fused score is under the threshold. No LLM call. This is the cheap guard: a question about property tax or Mumbai is caught before any money is spent.
- `model_abstained` — the model followed rule 3. The reason it gave is appended, so the user learns *why* the sources fell short.
- `citation_check_failed` — it answered twice and could not cite itself either time.

Two never reach the model at all, which is the main reason for the ordering of `answer_point`. Every abstention still carries the retrieval results and the zone lookup, so a refusal is informative rather than a dead end.

## D-046 · 2026-10-15 · Geocoding: Nominatim, bounded to Delhi, one request a second, cached
`app/geocode.py` turns a place name into coordinates so the agent can answer "what can I build near Dwarka Sector 21?" without a map click. It uses Nominatim, OpenStreetMap's free geocoder, because it needs no key, no account and no billing, which matters for a student project that must stay free to run. It is the only service other than Anthropic that this project calls.

Nominatim's usage policy is honoured rather than approximated. One request a second, enforced by a lock so it still holds when two requests arrive together once the agent runs behind the API; a 30 second timeout; and `User-Agent: ZoneWise/0.1 (student project)`, so the operator can see who is calling and complain to the right person.

The search is **bounded to a box around NCT Delhi** (76.80 to 77.40 east, 28.36 to 28.92 north, with `bounded=1` and `countrycodes=in`). Without that, "Mumbai Central" returns a point 1,200 km away, `get_zones` reports `inside_delhi: false`, and the user is told their plot is outside Delhi — technically true and completely unhelpful. Bounded, the same query returns nothing and the agent can say it could not find the place. The live check confirmed this: "Mumbai Central" came back `not_found_in_delhi`.

Results are cached in `data/index/geocode_cache.json`, gitignored like the rest of `data/index`. Misses are cached too, but only the honest kind: `not_found_in_delhi` is remembered, while `lookup_failed` from a timeout or a 500 is not, because a network failure says nothing about whether the name exists. Rejected: Google's Geocoding API (needs a key and a card), shipping a static gazetteer of Delhi place names (another dataset to maintain and keep correct), and unbounded search with a post-hoc distance check (one wasted request per out-of-area query, and the policy asks us to narrow the search instead).

## D-047 · 2026-10-15 · Three tools, and the agent may only cite what its own search returned
`app/agent.py` gives the model three tools and lets it sequence them, rather than hard-coding geocode-then-zones-then-search.

- `locate_place(query)` — a place name to coordinates.
- `get_zones(lat, lon)` — coordinates to the planning zones that contain them.
- `search_clauses(query, lat=None, lon=None, k=6)` — the clauses that match, location-aware when a point is given.

Why let the model decide the order: the questions are not all the same shape. "What can I build near Connaught Place?" needs all three. "Does MPD-2047 replace MPD-2021?" needs only the third. "Is 28.63, 77.22 in a TOD zone?" arrives with coordinates already and needs no geocoding. A fixed pipeline would either waste a geocoding call or fail on the cases it was not written for. Each tool's description says when to use it and what it returns, and `search_clauses` explicitly tells the model to pass coordinates whenever it has them, because that is what turns on exclusion, boosting and query expansion.

**The rule that makes agent citations trustworthy: a cited chunk id must have come back from a `search_clauses` call in this run.** This is a real risk rather than a theoretical one — the model can see the shape of a chunk id (`MPD47_GAZETTE_EN:4.2.3@p753:0`) and could produce a plausible one that points at nothing, or at a different clause. `AgentRun` therefore records every chunk id any search returned, and validation rejects anything outside that set. `tests/test_agent.py` covers both the invented id and the case where the model cites without having searched at all. Citing with no search is its own named problem, because an answer with confident citations and no retrieval behind it is the worst possible output.

Two smaller choices. `k` is clamped to 1-10, so a model asking for 500 clauses gets 10 instead of flooding the context. And a tool that fails returns `{"error": ...}` to the model rather than raising: a Nominatim timeout should let the agent say "I could not find that place", not end the request with a stack trace. Rejected: one combined `answer_about_place` tool (it would hide the steps, and the tool trace is one of the more interesting things to show a user), and letting the agent cite by clause number (clause numbers are not unique across this corpus — D-021 — so `4.2.3` could be the TOD norms or a Delhi Jal Board section).

## D-048 · 2026-10-15 · max_rounds = 4, and running out is an abstention
The agent loop is capped at four rounds: four model calls, each of which may ask for tools, before it must have written an answer. Four is chosen to fit the longest sensible path with one spare: locate_place, get_zones, search_clauses, answer. A model that is still calling tools on the fifth round is looping, not working.

Running out is an abstention with reason `max_rounds_reached`, not a half-answer and not an error. Whatever the tools did find is still returned in `retrieval` and `tool_trace`, so the interface can show the clauses and the steps even though no answer was written. The cap is in `app/config.py` and is passed as an argument, so a test can set it to 3 and assert the behaviour without waiting for four rounds. Rejected: no cap (an API bill that grows until something else stops it), and silently answering from whatever was gathered when the cap hit (that answer would not have been through the citation check).

## D-050 · 2026-10-15 · Without a key the app is still useful, and the 503 carries the clauses
Five of the seven endpoints need no API key: `/api/health`, `/api/zones`, `/api/layers/{name}`, `POST /api/search` and `/api/chunks/{id}`. Only `/api/ask` and `/api/agent` do. That split is the main API design decision, and it is what makes the project demonstrable today, with `.env` still holding a placeholder: a map of Delhi, click a point, see your planning zones, search the plan, read the clause. That is a working product without a single paid call.

When the two answering endpoints are called with no key they return **503 with the retrieval results included in the body**, not a bare error. `/api/ask` looks up the zones, runs the location-aware search, and sends back `{error: "no_llm", message: ..., zones: ..., results: [...]}`. The interface shows a "Search-only mode" notice and lists the clauses it found, so the user still gets the answer to their question — they just have to read it themselves. An error with nothing in it would turn a usable state into a dead end.

`llm_provider` is a FastAPI dependency returning `LLM | None` rather than raising, precisely so the endpoint can retrieve first and then decide. Being a dependency is also what lets `tests/test_api.py` override it with a scripted FakeLLM and test both answering endpoints, the 503 path and the 429 path with no key present. Rejected: a 200 with `answer: null` (a 200 means it worked), and hiding the endpoints when there is no key (the interface could not then explain what is missing).

## D-051 · 2026-10-15 · Two rate limits, in memory: 10 per minute per IP and 300 a day overall
`/api/ask` and `/api/agent` are limited; nothing else is, because nothing else costs money.

The per-IP limit is 10 a minute. It stops the ordinary accident — a browser tab in a retry loop, a double-clicked button — and it is per address so one noisy client cannot lock everyone else out.

The daily cap is 300 for the whole service, and it is the one that matters. It is the single thing standing between a bug and an unbounded API bill, which for a student project is the risk worth engineering against. It counts every answering request, whatever the address, and resets on the date changing.

Both live in a dict in one process. That is honest for what this is — one laptop, one uvicorn worker, no accounts — and it means no Redis and no extra dependency. Its limits are written down rather than discovered later: the counters reset when the process restarts, and a second worker would have its own copy. If ZoneWise ever runs more than one process, this has to move to a shared store, and the class is small enough to swap. A 429 explains itself in words a person can act on, including naming the setting to raise. Rejected: limiting by question text (a legitimate user asking the same thing twice would be blocked), and no cap at all.

## D-052 · 2026-10-15 · Every ask, agent and search request is logged as one JSONL line
`data/logs/requests.jsonl`, gitignored, one object per request: the time, the endpoint, the question, the zones found, the chunk ids retrieved, whether it abstained and why, the number of LLM calls and the latency.

Why keep it: this is the only record of what the system was actually asked, as opposed to what I guessed it would be asked. Tonight's 60 draft questions are my invention (D-054); the log is where real ones will come from, and the ones that abstained are the most valuable entries in it — they say what the corpus cannot answer. The retrieved chunk ids make a bad answer diagnosable after the fact: you can see exactly what the model was given.

Three deliberate constraints. The log never touches the settings object, so there is no path by which an API key could reach it. A logging failure is swallowed, because an unwritable log must never turn a working answer into a 500. And it is gitignored: it will hold whatever anyone typed into the box, which is not mine to commit. Rejected: logging the full answer text (it grows fast and the chunk ids plus the question are enough to reproduce it), and Python's `logging` module (a JSONL file is directly readable by the eval scripts, which is what this is for).

## D-053 · 2026-10-15 · Load everything once at startup, and serve simplified layers from memory
The embedding model, the Chroma collection, the BM25 corpus and the eight GeoJSON layers all load in the FastAPI lifespan, before the first request. Together they take a few seconds and about 80 MB; per request they would make a search take seconds instead of milliseconds.

A load failure is **recorded, not raised**, and `/api/health` reports it: `{"status": "degraded", "startup_errors": ["search index not loaded (...); run: uv run python scripts/05_build_index.py"]}`. A server that refuses to boot tells the user nothing; one that boots and names the script to run tells them exactly what to do. Endpoints that need the missing piece then return a 503 with the same message.

Map layers get a second cache. `/api/layers/{name}` simplifies geometry to 0.0005 degrees (roughly 50 m, far finer than a zone boundary is accurate anyway) and keeps the result in memory, so the cost is paid once per layer per process instead of once per page load. Only the five core layers are served; `regional_park`, `yamuna_river` and `low_density_area` are downloaded and loaded but not exposed, because nothing in the product uses them yet and an endpoint nobody calls is still an endpoint to maintain.

One routing detail worth recording: `/api/chunks/{chunk_id:path}` uses the path converter because chunk ids contain colons and `@` after the collision fix (D-021) — `MPD47_FAQ:Q13@p13:0` — and the default converter would not match them.

## D-054 · 2026-10-15 · The 60 questions are drafted, unverified, and cannot be reported
`eval/questions_draft.jsonl` holds 60 questions I wrote by reading the chunks: 25 location questions, 25 general ones and 10 that should be refused. Every record has `verified: false`, and `eval/run_eval.py` refuses to score any of them unless `--include-unverified` is passed, in which case every output file is prefixed `DRYRUN_` and carries a banner reading "DRY RUN - UNVERIFIED QUESTIONS - NOT FOR RESUME OR REPORTING".

The reason for all that machinery is a real problem, not a formality. These questions were drafted **from the same text the retriever searches, by the same model that built the retriever**. A score against them measures how well the retriever agrees with its own author. Tonight's dry run put `hybrid+location` at recall@5 of 0.74 against `hybrid` at 0.56 — a number that looks like a result and is not one, which is exactly why the banner exists.

Verification cannot be delegated to the thing being measured, so `eval/README.md` sets out the procedure for a person: open the expected chunk with `scripts/show_chunk.py`, check that it answers the question, check the one-line expected answer, **rewrite the question in your own words** (the step that matters most, because the phrasing is then independent of the corpus), fix the expected ids, set `verified: true`. The verified lines go in `eval/questions.jsonl`, which `run_eval.py` prefers and which the drafting script never overwrites. Rejected: marking my own questions verified (the whole point is a second pair of eyes), and skipping the draft (a blank file is no easier to verify than a draft, and this way the shape of the set, the categories and the coverage are already decided).

## D-055 · 2026-10-15 · Two leakage rules, enforced in code, not trusted
`scripts/09_draft_questions.py` checks every question it writes and exits non-zero if any check fails.

**No run of four or more consecutive words may be copied from any chunk the question points at**, expected or acceptable. A question that quotes its own answer tests nothing: BM25 finds it by string overlap and the score says the retriever works when all it has shown is that two pieces of text share a phrase. The check builds the 4-grams of the question and intersects them with the 4-grams of each chunk. All 60 pass; the guard was tested against a deliberate violation ("What is the minimum area of 2000 sqm for a TOD Plot?" correctly reports `area of 2000 sqm` and `minimum area of 2000`).

**A location question may not name its zone or topic.** Any of "tod", "transit oriented", "high density", "hdc", "uer", "urban extension", "land pooling", "pooled land", "zone o", "yamuna", "floodplain" in a location question means the question is a keyword search wearing a costume. "How much of the land am I allowed to cover with building?" asked at a point in a TOD zone is the real test, because only `get_zones` can supply the word TOD. All 25 location questions pass.

Three more checks ride along, because they are cheap and each one caught something while drafting: every expected and acceptable chunk id must exist in `chunks.jsonl`; a non-abstain question must have 1 to 3 expected ids; and an abstain question must have none. Rejected: a similarity threshold instead of exact n-grams (a number to tune, and n-grams are the thing actually being guarded against), and checking leakage by hand (60 questions times several chunks each, re-checked on every edit).

## D-056 · 2026-10-15 · recall@k, MRR, and bootstrap intervals rather than bare averages
`eval/metrics.py` reports recall@1, @3, @5 and MRR against the union of each question's expected and acceptable chunk ids, overall and per category, for four configurations: dense, bm25, hybrid and hybrid+location.

recall@k is the headline because it matches what the pipeline does with the result: the top k chunks go into the prompt, so if the right clause is in the top 5 the answer can be grounded, and if it is not, nothing downstream can save it. MRR is reported alongside because recall@5 cannot distinguish "found it first" from "found it fifth", and the position is what a user experiences.

**Every headline number carries a bootstrap 95% confidence interval** over 1,000 resamples with a fixed seed. With 50-odd questions, a recall of 0.74 could easily have been 0.62 or 0.86 on a different set, and quoting 0.74 alone hides that. The interval makes the honest statement — "this question set is too small to separate these two configurations" — available as a finding rather than something to be quietly skipped.

The hybrid+location comparison is **paired**: per question, (did location find it?) minus (did hybrid find it?), then bootstrapped. Pairing cancels the variation caused by some questions simply being harder, which is the dominant source of noise when both configurations answer the same 25 questions. Tonight's dry run shows the value of saying this properly: the recall@5 difference was +0.360 with an interval of [+0.160, +0.560], excluding 0, while the recall@1 difference was +0.120 with [-0.080, +0.320], which includes 0 and therefore says nothing. One of those is a claim; the other is not. Rejected: a t-test (it assumes a distribution that a 0/1 metric over 25 questions does not have), and reporting means with no uncertainty at all.

## D-057 · 2026-10-15 · The abstention threshold is chosen by a sweep, not by taste
`run_eval.py` ends with a retrieval-only sweep: for each candidate threshold from 0.002 to 0.05, the share of should-abstain questions whose top fused score falls below it (caught) against the share of answerable questions that would be wrongly refused (lost), and it suggests the threshold with the widest gap. No LLM call is involved, which is the point — this decides whether the cheap guard in `answer_point` can work at all.

Ties go to the **lower** threshold. Wrongly refusing a real question is worse than letting an unanswerable one through: the first denies someone an answer the documents do contain, while the second still has the citation check behind it.

Tonight's dry run is already informative, with the caveat that it comes from unverified questions. The configured placeholder of 0.02 catches **0%** of the should-abstain questions — the sweep's first ten rows are all zeroes — while the widest margin sits around 0.032, catching 50% of them at the cost of wrongly refusing 16% of answerable ones. So the placeholder is almost certainly too low to do anything, and the real value is probably near the 2/61 = 0.0328 that a chunk ranked first by both indexes scores. That is a prediction to test on Day 5 with verified questions, not a change to make tonight. Rejected: tuning the threshold on the drafts (it would be fitted to my own questions), and dropping the pre-check entirely (every unanswerable question would then cost a call).

## D-060 · 2026-10-15 · Search-only mode is a designed state, not an error screen
With no API key the interface still works, and that was the main thing shaping it. `/api/health` reports `llm_available`, and when it is false the panel carries a standing notice: the map, the zones, the clause search and the clause reader all work; questions return the clauses to read instead of a written answer.

Asking a question in that state is a 503 from `/api/ask` carrying the retrieved clauses (D-050), which the interface catches by its `error` code rather than treating as a failure, and renders as a list of clauses with their pages, each opening the full text. The effect is that the project demonstrates fully today, with no key and no spend. ## D-061 · 2026-10-15 · Citations are chips that open the clause, and the two marker formats are unified
A citation in the answer is rendered as a small numbered chip. Clicking it opens a drawer with the clause in full, the document title, the chapter, the heading path, the clause number, the page range, the authority rank in words, and a link to the source PDF. That is the whole point of citing: a citation nobody can follow is decoration.

The two endpoints cite differently, which the renderer has to absorb. `/api/ask` emits `[C1]`, `[C2]` against the numbered sources it was handed, because the model never sees chunk ids. `/api/agent` emits the whole chunk id, `[MPD47_GAZETTE_EN:4.2.3@p753:0]`, because it chose what to retrieve and the chunk id is the only thing that can be checked against what came back (D-047). Rather than teach the interface two formats, both results carry a `citations` array whose `marker` field holds whatever was used, and the renderer looks up each bracketed token in that array, displaying its position rather than its raw text. A bracketed token that is not a known citation is left as plain text, so a model writing `[sic]` does not produce a dead chip.

Abstentions get their own state in the same panel rather than an empty result: a heading, a plain-English explanation of the specific reason (`outside_delhi`, `weak_retrieval`, `citation_check_failed`, `model_abstained`, `max_rounds_reached`), the model's own words where it gave them, and a line saying that declining is deliberate. The retrieved clauses are shown expanded underneath, because a refusal with the relevant clauses attached is still useful. The agent's tool trace sits in a collapsed `details` element, since the sequence of steps is the interesting part of agent mode but not what the user came for.

## D-065 · 2026-10-17 · Every setting is read from the environment, and a bad value is not fatal
`app/config.py` gained five readers — `env_str`, `env_int`, `env_float`, `env_bool`, `env_list` — and every setting a deployment might change goes through one of them with the value in the file as its default. The reason is the deploy kit (D-076): a container is configured with variables, so anything that still needs editing inside the image is a setting that cannot be changed in production.

The readers are deliberately forgiving: `RATE_LIMIT_PER_MINUTE=ten` falls back to 10 rather than raising, and a blank value is treated as unset. The exception is deliberate too: nothing silently repairs the API key, because `looks_like_api_key` has to stay strict (D-040), and a wrong key must read as no key. Rejected: pydantic-settings (a new dependency for five five-line functions), and raising on a malformed value (it turns a typo into an outage).

## D-066 · 2026-10-17 · The chunk audit, and the five systematic defects it found
`scripts/audit_chunks.py` runs eight mechanical checks over `chunks.jsonl` and writes a count plus five examples each. It exists because every retrieval number in this project is capped by chunk quality and none of the retrieval metrics can see it: a clause cut in half still gets retrieved, still gets cited, and reads as a model error rather than an extraction error.

The audit found five causes worth fixing, all in cleaning or chunking, each now with its own tests:

**1. Divider titles spread over several lines.** `DIVIDER_LINE` removed "CHAPTER 7. DEVELOPMENT CONTROL NORMS (DCN)" and left "FOR RESIDENTIAL" on the next line, which then became the last words of the previous chapter's final clause — "...Police Post, Fire Station and Post office. FOR COMMERCIAL". A divider line **printed in capitals** now opens a divider block, and the capitalised lines under it go too. Three guards keep it narrow: the opening line must be capitals, so the contents entry "Part I: Background" in the middle of 384 words of prose on page 647 does not open a block; a continuation must be capitals, at most ten words, and end without sentence punctuation; and a line that starts with its own number or the word Annexure is never a continuation, because "4.2 TRANSIT ORIENTED DEVELOPMENT (TOD)" can legitimately sit under a chapter divider. Run across all 560 pages the rule drops exactly the ten divider-title lines and nothing else.

**2. A sentence cut at a page break.** `scripts/03_chunk.py` inserted a blank line — a paragraph break, which is where the chunker may cut — between every pair of pages. Page 683 of the gazette opens "and seamlessly integrated with the green spaces and floodplains", and the chunker duly started a chunk there. `cleaning.join_pages()` now joins the two lines instead when the earlier one does not end a sentence **and** the later one starts with something that cannot start one (a lower-case word, or "and", "however" and the like). Both conditions are needed: a heading has no full stop either. It fires at 57 page breaks in this gazette, and the joined line keeps the earlier page as its start and the later as its end so the page range stays honest.

**3. An empty table header.** PyMuPDF reads some table top borders as a row of empty cells, so `table_to_markdown` was writing an all-empty row as the header — and `split_markdown_table` repeats the header on every piece, so one empty row became several. Leading all-empty rows are now dropped. Only leading ones, and they are never reordered: the first printed row with content becomes the header, in document order.

**4. A heading that could not reach its own content.** "Annexure 9: List of permissible Household Industries" was a seven-word chunk, because `_can_fold_into` compared dotted clause-number prefixes and "Annexure 9" shares none with "Annexure 9a". It now also folds when the next section names the carried heading in `parent_key`, which is the relationship the sectioniser already recorded. Two seven-word chunks disappeared.

**5. A table title stranded at the end of the chunk before it.** Packing fills a chunk until the next unit will not fit, which regularly left "Table 2 Water Augmentation Action Plan" as the last line of one chunk and the table as the first thing in the next — both halves worse for it. `_move_orphan_titles` moves such a line forward when it is its own paragraph, at most fifteen words, ends without sentence punctuation, leaves something behind, and fits.

## D-067 · 2026-10-17 · Chunk ids are remapped by text overlap, never by hand
Changing the chunking rules moves chunk ids, because an id encodes where its chunk starts (`MPD47_GAZETTE_EN:4.2.3@p753:0`). The 60 drafted evaluation questions point at 97 chunk ids, and a question whose expected id no longer exists scores zero against every configuration — which looks exactly like a retrieval failure and is not one.

`scripts/remap_eval_ids.py` takes the previous `chunks.jsonl`, reads the text each referenced id used to hold, and finds the new chunk whose text best covers it. Overlap is measured asymmetrically — what share of the **old** chunk's words the new chunk still contains — because the question was written about the old content: a new chunk that absorbed its neighbour is still the right target, while one holding half the old text is not. An id that cannot clear 50% is left alone and its question is flagged `notes="remap_failed"`, on the principle that a wrong expected id is worse than a missing one, since the first measures the wrong thing silently. The script never touches a question's text, its category, its `should_abstain` flag or its `verified` flag; that is a person's job (D-054).

Tonight it was a **verified no-op**: all 97 ids still exist and all 97 still cover their old text, so nothing was re-pointed and `eval/questions_draft.jsonl` came out byte-identical. The evidence is in `eval/remap_log.json`, one row per id. That is worth having recorded rather than assumed — the alternative was to look at two chunk counts, see 702 and 700, and guess.

To get the old chunks to compare against, the pre-fix code was checked out into the scratchpad with `git archive` and `03_chunk.py` re-run there against a copy of `pages.jsonl`. `data/processed` is not committed, so there was nothing to diff against otherwise.

Rejected: remapping by id pattern (the id is the thing that moved); re-drafting the questions against the new chunks (it would throw away the leakage checks that passed and the categories that are balanced); and assuming the ids were fine because the count only moved by two (two chunks disappearing can renumber a whole document's trailing suffixes).

## D-070 · 2026-10-17 · The cross-encoder reranker exists, is measured, and stays off
`fastembed.rerank.cross_encoder.TextCrossEncoder` **is** available in the installed fastembed 0.9.0, which offers eight cross-encoders. The smallest MS-MARCO one is `Xenova/ms-marco-MiniLM-L-6-v2` at 0.08 GB, and that is the one `app/rerank.py` uses, cached in `data/index/models` beside the embedding model so a container image carries it. `available()` is checked rather than assumed, because the module arrived in a later fastembed than this project first pinned, and `eval/run_eval.py` drops the rerank configuration and says so in the report when it is missing.

**What a cross-encoder is, and why it can help.** Both existing indexes compare query and chunk *separately* — the chunk vector is computed at index time, without knowing the question, which is exactly what makes searching 700 chunks fast. A cross-encoder reads query and chunk together as one input and returns a single relevance score. It cannot be precomputed, so it cannot search a corpus, but it can rescore a shortlist. Fusion picks the top 20, the cross-encoder reorders them, the top k of that is returned.

**What it costs, measured rather than guessed.** 2.4 s a query against 0.031 s without it on this laptop's CPU — about **77 times the cost of the entire search that produced the shortlist**. The first version of this decision said "about 0.4 s"; that was a guess and it was wrong by a factor of six, which is why the number is now a measurement over five queries.

**What it buys, on questions that cannot prove anything yet.** In tonight's dry run over the 60 drafted questions, `hybrid+location+rerank` scored recall@1 0.460 against `hybrid+location`'s 0.340, recall@5 0.780 against 0.720, and MRR 0.580 against 0.486. That is a large and consistent gain, and it is **not evidence**: the questions were drafted by Claude from the chunks the retriever searches (D-054), and a cross-encoder reading query and chunk together is precisely the component that would benefit most from a question phrased in the chunk's own words. The reranker could be flattering itself on exactly the circularity the verification step exists to remove.

So `use_reranker` defaults to **false** and the decision is deferred to the verified set, with the configuration already scored so the answer arrives for free. On the evidence available the gain looks real enough to be worth the latency for a one-question-at-a-time interface; that is a prediction to test, not a setting to change tonight.

Two details that are decisions rather than defaults. The reranker is handed the **expanded** query — the same text both indexes searched with — so it judges the question the retrieval actually asked, including the zone words location-aware search added. And a reranker failure is caught, recorded in `SearchReport.rerank_error` and followed by returning the fused order: the reranker is an optimisation, and losing it should cost result quality, not the answer.

Rejected: a larger cross-encoder (`BAAI/bge-reranker-base` is 1.04 GB, 13 times the size, for a corpus of 700 chunks); reranking the whole fused pool rather than 20 (the cost is linear in the shortlist and the 21st fused result is rarely the answer); and turning it on because the dry-run numbers look good (the whole point of the dry-run banner).

## D-071 · 2026-10-17 · The abstention signal is a raw score, and the threshold is provisional
The pre-check in `answer_point` read `results[0].fused_score` against `abstain_threshold`. That was wrong in a way worth spelling out, because it looked right for two nights.

**An RRF score encodes rank position and nothing else.** A chunk both indexes ranked first scores 2/(60+1) = 0.0328 — whatever was asked. A question about property tax in Mumbai and a question the gazette answers in full both produce 0.0328 if their best chunk topped both lists. The guard was reading a number that is constant with respect to the thing it was trying to measure. Tonight's dry run shows it directly: under `hybrid+location`, the median top fused score is **0.0328 for answerable questions and 0.0310 for should-abstain ones**. Those two rows sit in `eval/results/DRYRUN_night3_*.md` so the point can be read rather than taken on trust.

**So every result now carries its raw scores**: `dense_cosine` (cosine *similarity*, computed as 1 − the distance Chroma returns, because similarity runs the right way round), `bm25_score`, and `rerank_score` with `rerank_rank` when the cross-encoder ran. `retrieval.signal_value()` is the one place a signal is read by name, so the pre-check, the API's score breakdown and the evaluation's percentile tables cannot drift apart.

**`settings.abstain_signal`** chooses between `dense_cosine` (the default) and `rerank_score`. Asking for `rerank_score` with the reranker off falls back to the dense signal rather than silently disabling the guard — every result would have `None` and everything would pass. A result with no value for the signal is **not** treated as weak: a chunk only the keyword index found has no cosine similarity, and that is a gap in what we know, not evidence against it.

**The threshold is PROVISIONAL, and labelled so everywhere** — in `app/config.py`, in `.env.example`, in the evaluation report and in `eval/README.md`. `scripts/tune_abstention.py` measures the signal over a question file and names two values: the highest threshold that refuses *none* of the answerable questions, and the widest-margin one. Only the first may be used before a person has checked the questions, because anything that trades a real answer away has been fitted to the set.

Measured over the 60 drafts:

| signal | answerable p5 / p50 / p95 | should-abstain p5 / p50 / p95 | provisional | widest margin |
| --- | --- | --- | --- | --- |
| `fused_score` | 0.0301 / 0.0328 / 0.0488 | 0.0285 / 0.0310 / 0.0488 | — | 0.0321 (catches 60%, loses 20%) |
| `dense_cosine` | 0.6371 / 0.7349 / 0.8303 | 0.5834 / 0.6765 / 0.7655 | **0.5804** | 0.6988 (catches 60%, loses 22%) |
| `rerank_score` | −8.479 / 1.344 / 8.022 | −9.680 / −4.451 / 4.172 | −10.238 | 1.233 (catches 90%, loses 44%) |

So the configured default is `ABSTAIN_SIGNAL=dense_cosine` with `ABSTAIN_THRESHOLD=0.5804`, which refuses none of the 50 answerable drafts and catches none of the 10 should-abstain ones. **That is the honest result and not a broken guard**: at this threshold the pre-check only catches a total retrieval failure, because the two distributions overlap almost entirely on this signal. BGE embeddings compress everything into a narrow similarity band — unrelated text still scores 0.6 — so cosine similarity separates these two groups weakly. The cross-encoder separates them far better in the middle (medians 1.34 against −4.45, two and a half points apart on a scale where the dense medians differ by 0.06) but has a long low tail of answerable questions, so its provisional value is also useless and its useful value loses 44%.

The conclusion to carry into Day 5 is that **no single retrieval score cleanly separates these ten should-abstain questions from the fifty answerable ones**, and the thing standing between an unanswerable question and a confident wrong answer is still the model's own rule 3 and the citation check behind it (D-043, D-045). The pre-check is a cost guard, not a correctness guard, and it should be set to the value that spends the least while losing nothing.

**A bug in the first version of the tuning script is worth recording**, because it is the same class of error as the fused-score mistake. `provisional()` returned `max(0.0, min(answerable) - margin)`. The clamp is harmless for a cosine similarity and actively wrong for a cross-encoder score: the lowest answerable draft scored −10.2, so the clamp turned "refuse nothing" into a recommended threshold of **0.0, which would have refused 40% of the answerable questions**. A guard written for one signal's range inverted its own meaning on another's. The clamp is gone, `eval/metrics.sweep_thresholds()` now derives its candidates from the range the scores occupy instead of the fixed 0.002-to-0.05 list that only ever suited RRF, and `.env.example` says in as many words that the threshold must be reset whenever the signal changes.

Rejected: normalising the three signals onto one scale so a single threshold works for all of them (the normalisation would have to be refitted whenever the corpus or the model changes, and it would hide exactly the scale difference that caused the bug); keeping the fused score as a secondary condition (two guards, neither understood); and dropping the pre-check entirely now that it is known to be weak (it still catches an empty result set, and it is the only thing between a bug and a bill).

## D-072 · 2026-10-17 · The evaluation turns the reranker on per configuration, not per process
`eval/run_eval.py` scores five configurations in one pass, and one of them needs the reranker on while the other four need it off. `USE_RERANKER` is read once at import, so a process-wide flag cannot express that.

## D-073 · 2026-10-17 · Four steps to a point, and the Dwarka miss is fixed
`locate_place` was one bounded Nominatim request with `limit=1`. Night 2's live check found that this returns **nothing** for "Dwarka Sector 21 metro station" (D-049) — a real station, well inside the viewbox, and close to the phrase the agent's own example box suggests typing. One geocoder's indexing of one naming convention should not be the only thing between a user and an answer, so there are now four steps, tried in order, with the step that answered recorded on the result.

**1. Normalise.** Lower case, punctuation out, then two different kinds of word removed two different ways. Proximity words ("near", "nearest", "close to") go wherever they appear, because no Delhi place name contains one. Station words ("metro station", "metro", "station", and the trailing ", New Delhi") come off the **end only**, repeatedly, because they do appear inside place names. The first version stripped them anywhere and turned **"Station Road" into "road"** — the docstring at the time claimed it did not, which is exactly the kind of claim worth checking against the code. Metro Vihar and Delhi Gate survive for the same reason. A preposition stranded at either end goes too, so "near the Yamuna in Delhi" reduces to "yamuna" rather than "yamuna in".

**2. The gazetteer.** `scripts/build_gazetteer.py` makes **one** Overpass request for Delhi Metro stations inside the NCT bounding box and writes `data/gazetteer/metro_stations.json`: name, alternate names, latitude, longitude. `locate_place` fuzzy-matches the normalised query against every name and alternate with `difflib.get_close_matches` at cutoff 0.85, and accepts the match **only when it is unique**. Ambiguity is refused rather than guessed: when two station names are equally close, the query has not identified either, and choosing between "Civil Lines" and "Civic Centre" is worse than falling through to Nominatim. A station appearing under two of its own names is not ambiguous, and that case is handled separately.

The gazetteer is tried before Nominatim because it is free, instant and local, and because a metro station is the commonest way a Delhi resident describes where they are. It is gitignored — the data is OpenStreetMap's under the ODbL, and one script call rebuilds it — and the attribution **© OpenStreetMap contributors** is recorded in README.md and docs/DATA.md.

**3. Nominatim, twice at most.** The user's own words plus ", Delhi", then the normalised form plus ", Delhi". Two attempts rather than the five a `limit=5` sweep would allow, because each request costs a second of someone else's donated capacity and the second phrasing is the one most likely to differ in result. A timeout or a 500 **stops** the sequence instead of spending the second request: a service that is currently unhappy says nothing about whether the name exists.

**4. not_found**, with the reason and the path, rather than a point somewhere else.

**The live check, 7 of the 8 requests the brief allowed:**

| query | result | path | point |
| --- | --- | --- | --- |
| "Dwarka Sector 21 metro station" | **found** | `nominatim_normalised` | 28.55192, 77.05856 — in Delhi |
| "near Rajiv Chowk" | found | `nominatim_normalised` | 28.63177, 77.21938 — in Delhi |
| "Hauz Khas" | found | `nominatim_original` | 28.54981, 77.20776 — in Delhi |
| "Connaught Place" | found | `cache` | 28.63177, 77.21938 — in Delhi |
| "Mumbai Central" | **not found** | `not_found` | correct: the box excludes it |

The Dwarka miss is fixed, by the normalisation step rather than the gazetteer: stripping "metro station" and appending ", Delhi" is enough. `get_zones` confirms all four hits are inside NCT Delhi, which is a stronger check than the bounding box.

**A cached miss had to be invalidated, and this is the part worth remembering.** The first run of the live check reported "Dwarka Sector 21 metro station" as *still* not found — from night 2's cache. That entry was true of the lookup that wrote it and false of this one, and it would have made a working fix look broken while the code was perfectly correct. A remembered **hit** stays valid, because a place does not move. A remembered **miss** is a statement about the algorithm as much as about the name, so `is_stale_miss` discards a miss recorded without a `path` field — the field the four-step lookup always writes. Rejected: raising `limit` to 5 and taking the first result `get_zones` likes (D-049's first suggestion — it spends up to five results' worth of someone else's capacity per query, and the normalisation step turned out to be enough); retrying without `bounded=1` and testing against the NCT polygon (D-049's second suggestion, kept in reserve: it is strictly better than a box, but it needs a request that may return a point 1,200 km away, and nothing in the live check needed it); shipping a hand-written list of Delhi place names (D-046 rejected this and was right — a dataset to maintain by hand); and matching the gazetteer with a similarity threshold but no uniqueness test (it would answer confidently for any query that is vaguely like two stations).

The script prints the count, the number of OSM elements behind it, and the first and last station name for exactly that reason.

## D-075 · 2026-10-17 · The verification endpoints are behind a flag and 404 without it
Four endpoints under `/api/dev/eval/` serve the verification screen: list the questions, get one with its chunks and current top 5, check a rewritten question for leakage, save a decision. All four read and write files under `eval/`, and the last one writes `questions_verified.jsonl`, so none of them has any business being reachable on a deployed server.

`require_dev_mode` is a FastAPI dependency that raises **404**, not 403, unless `ZONEWISE_DEV=1`. A 403 confirms the endpoint exists and that the flag is the thing standing between you and it; a 404 is indistinguishable from a path that was never written. `/api/health` reports `dev_mode`, which is how the frontend decides whether to show the Verify tab — so the flag is read in exactly one place on each side, and the browser's copy is a convenience rather than a second access control.

`app/dev_eval.py` deliberately does **not** check the flag. A module that reads and writes evaluation files is not a security boundary, and putting the check in both places would leave the authority in neither. The endpoints are the boundary; the tests assert all four are 404 with the flag off and working with it on.

The default is off: `env_bool("ZONEWISE_DEV", False)`, so a container that forgets to mention it is safe rather than exposed. `.env.example` says in as many words not to set it in production.

Rejected: a shared-secret header instead of a flag (a secret that lives in `.env.example` is not a secret, and the screen is for one person on localhost); serving the screen from a separate app on another port (two servers to start, and the screen needs the same loaded index as everything else); and leaving the endpoints always on because the project has no users yet (the deploy kit exists in the same night's work, so "no users yet" stopped being true in Stage 7).

## D-076 · 2026-10-17 · The verification screen, and what its shape is for
Verifying 60 questions by editing JSONL in an editor means, per question: find the line, read the expected chunk id, run `show_chunk.py` in another terminal, read the clause, decide, maybe run `search.py` to find a better one, edit three fields, re-check the leakage rule by hand, save. Three hours of that is how a necessary task becomes one that does not get done — and the evaluation is the thing standing between this project and any number it can report (D-054).

So the work gets a screen, and its shape follows the shape of the job. Verifying one question means answering four things — does the expected clause really answer this, is the one-line answer right, would a person ask it this way, does the rewrite still avoid naming the zone — and **all four need the clause text and the retrieval results visible at the same time as an editable question box**. So everything is on one wide screen, and the keyboard does the navigation: A accept, E save edit, R reject, S skip, arrows to move. Shortcuts are ignored while the caret is in a text box, because typing "a" in a question must not accept it.

Four details are decisions rather than defaults.

**Rejected and skipped questions are written down.** A rejected question goes into `questions_verified.jsonl` with `verified: false` and `status: "rejected"`. Without that record, "I read this and it is a bad question" is indistinguishable from "nobody reached this one", and the second is the state you want to find when you come back tomorrow. `run_eval.py` skips anything without `verified: true`, so a recorded rejection is never scored.

**The draft file is never written.** `scripts/09_draft_questions.py` owns it and regenerates it, and a test asserts the bytes do not change across a save. The record of what was generated survives, and re-running the drafter cannot destroy an evening of verification.

**The leakage check runs on the rewritten text, live, and again on save.** Rewriting the question in your own words is the step that makes it independent of the corpus (D-055), and it is also the step most likely to accidentally quote the clause sitting open on the screen beside it. The live warning is a convenience; the check on save is the enforcement, and a decision that fails it is refused with a 422 naming the phrase, because the person typing is the one who has to fix it.

**The expected clause is shown in full, in a `<pre>`.** Not a snippet — the question is whether this clause answers that question, and a 200-character preview cannot answer it. `<pre>` rather than a paragraph because a gazette clause carries markdown tables and indented sub-items, and collapsing that whitespace makes a norms table unreadable.

The same guards the drafter enforces on its own output are enforced on a hand-edited decision: the chunk ids must exist in the index, an answerable question needs 1 to 3 expected ids, a should-abstain question needs none, and nothing may quote its own answer. More so for a hand-edited one, in fact, since nothing else will look at it again.

The tab is plain state in `App.jsx`, not a router. There are two views, one of which only exists in dev mode, so a routing package would be the seventh npm dependency for a boolean (D-059). `eval/README.md` is rewritten around the screen, with the exact PowerShell steps, how many questions to keep in each category, and two worked examples of a good rewrite against a bad one.

`run_eval.py` now reads `questions_verified.jsonl` first, then `questions.jsonl` (the hand-edited file night 2's README described, still read so that work is not orphaned), then the drafts.

`eval/questions_verified.jsonl` is **committed**, not gitignored. It was briefly added to `.gitignore` while writing this, on the reflex that generated files under `eval/` are not committed, and that was wrong: this file is not generated, it is the output of two hours of a person's judgement, it is a few kilobytes, and CLAUDE.md already lists the verified question set among the committed files. Losing it to a clean checkout would be losing the only part of the evaluation that cannot be rebuilt by a script.

One bug the tests caught is worth recording because it would have been invisible in use: `save_decision` reported where it had written by calling `relative_to(project_root)`, which raises for any path outside the repo. It only showed up because the tests point the module at a tmp folder — but the same call would have raised for a checkout at an unexpected root. A message saying where a file was written must not be able to fail; `shown_path` falls back to the absolute path.

Rejected: a Jupyter notebook for the verification (it would need a seventh dependency and a kernel, and it cannot show a map); editing the JSONL by hand with better instructions (that was night 2's answer, and three hours of context-switching is the reason to replace it); and writing accepted questions straight into `questions.jsonl` (it would mix generated and verified records in one file, which is the thing D-054 separated).

## D-077 · 2026-10-17 · Input validation, a body limit, and four security headers
The API is read-only and has no accounts, so the things worth hardening are the ones that cost nothing and close a real hole. Four changes.

**Every length now comes from config.** `question` was `max_length=1000` in three request models; it is `settings.max_question_chars` (500) in all three, from `MAX_QUESTION_CHARS`. A limit that cannot be changed in a deployment is not a limit, it is a constant.

**A body-size check in middleware, before parsing.** `Content-Length` over `MAX_REQUEST_BYTES` (64 KiB) gets a 413 naming the limit. Reading the header rather than the body means an oversized request is refused without being read into memory. A request that declares no `Content-Length` is *not* refused here — there is nothing to check yet, and the field limits catch it a moment later.

**Latitude and longitude keep their full valid ranges**, −90 to 90 and −180 to 180, deliberately not a Delhi bounding box. A point in Gurugram is a legitimate request with an honest answer — `outside_delhi`, no LLM call (D-045) — and validating it away at the edge would turn a useful reply into a validation error.

**One readable sentence for a 422.** FastAPI's default body is a list of dicts with `loc`, `type` and `ctx`: precise, and unreadable in an interface that shows `detail.message`. A `RequestValidationError` handler now produces `"query: String should have at most 500 characters"` and keeps the raw errors under `errors` for whoever is debugging a client.

**Four headers on every response**, chosen because each closes something real rather than to fill a scanner's checklist: `X-Content-Type-Options: nosniff` (a JSON body must not be sniffed as HTML and run), `X-Frame-Options: DENY` (nothing here should be framed by another site), `Referrer-Policy: no-referrer`, and `Permissions-Policy` turning off geolocation, camera and microphone — the map asks the user to click a point, and never asks the browser where they are. There is no Content-Security-Policy, and that is a deliberate omission rather than an oversight: the map loads tiles from OpenStreetMap and marker images from unpkg, so a CSP strict enough to be worth having would need those origins enumerated and would break the moment a tile server changed. It belongs with a real deployment, and `docs/DEPLOY.md` is where it would go.

**CORS comes from config**, as `CORS_ORIGINS`, comma-separated — the default is still the Vite dev server, and `docs/DEPLOY.md` says to set it to your own site and nothing else.

**The map now credits both sources**: "© OpenStreetMap contributors · Boundaries: DDA GIS portal". The boundaries are the part a user might act on, and they are someone else's work. There is still no bulk download endpoint — `/api/layers/{name}` serves geometry simplified to about 50 m for drawing, which is what a browser needs and not a redistribution of DDA's data (D-030).

Rejected: a Delhi bounding box on the coordinate validation (it would reject the one question with the clearest honest answer); a CSP guessed at tonight (see above); and rate limiting the five key-free endpoints (they cost nothing but CPU, and the thing worth protecting is the API bill).

## D-079 · 2026-10-17 · The image carries the built data; the Docker build could not be run
**The Dockerfile is two stages**: `node:20-slim` builds `web/dist`, then `python:3.12-slim` runs `uv sync --frozen --no-dev` and copies `app/`, `scripts/`, `eval/`, the built frontend, and the four generated data directories — `data/processed`, `data/index` (including the cached embedding and reranker weights), `data/layers` and `data/gazetteer`.

**Baking the data in rather than building it at startup** is the main decision. Embedding 700 chunks takes about 160 seconds on a CPU and downloading the two models takes longer, so a container that built its own index would spend three minutes before its first request and do it again on every restart and every replica. The cost is that `docker build` must run on a machine where the pipeline has already run, which is why `docs/DEPLOY.md` says so first and in bold, and why the health check asks for `status == "ok"` rather than for a 200: a container with no index starts, reports `degraded`, and serves 503s, and a health check that only wanted a 200 would call that healthy.

Four more details are decisions. `data/raw` and `.env` are excluded by `.dockerignore` **and** never named in a `COPY`, because a key baked into a layer stays in that layer forever even if a later layer deletes it. The container runs as a non-root user, and `data/logs` is created and chowned at build time, because `log_request` swallows its errors by design (D-052) and a container that could not write its log would lose every request record silently. Dependencies are copied and installed before the source, so editing a Python file does not re-resolve 107 packages. And the CMD runs **one** uvicorn worker: the rate limiter and the daily cap are in-memory (D-051), so a second worker would have its own counters and the cap that protects the API bill would silently double.

**The build could not be run, and that is recorded rather than worked around.** `docker --version` and `docker info` both answer in under a second, so the daemon is there — but `docker pull python:3.12-slim` produces **zero bytes and times out**, exactly as `overpass-api.de` did (D-074). The registry is unreachable from the sandbox this session runs in. A full `docker build` was left for fifteen minutes and produced no output at all. Two honest attempts, so it is recorded as skipped.

What was verified instead, because "it probably builds" is not a thing to write down:

- **Every `COPY` source exists.** A script walks the Dockerfile and checks all sixteen paths, including that the optional `web/package-lock.json*` glob matches. The commonest way this Dockerfile could fail is a path that is not there, and that one is now checked rather than assumed.
- **No `.dockerignore` pattern excludes anything a `COPY` names.** The second commonest failure, and a silent one: the build succeeds and the image is missing its index.
- **`uv sync --frozen` is consistent** with the committed lockfile — "Checked 107 packages, would make no changes" — so the step that would fail hardest in a build passes locally.
- **The exact CMD was run outside a container** and smoke-tested: `uvicorn app.api:app --host 127.0.0.1 --port 8123 --workers 1`, then `/api/health` returning `status: "ok"` with 700 chunks and no startup errors, `/api/zones` at Rajiv Chowk returning planning zone D with `tod: true`, `/api/layers/regional_park` returning its 44 features, the security headers present, and the built frontend served at `/`. That tests the command, the settings, the loading and the serving — everything the image would do except being an image. **The HEALTHCHECK's own expression was evaluated and exits 0.**

So the remaining risk is narrow and worth stating plainly: the layer caching, the two `uv sync` invocations and the non-root log directory are untested, and `docker build` is the first thing on the remaining-work list.

`docs/DEPLOY.md` covers it end to end for someone who has not done this before: build the data first, build and check the image locally, launch a `t3.small` (not a `micro` — the model and layers need about 400 MB and a micro has 1 GB), three security-group rules with 8000 closed and SSH open only to your own address, `docker save | gzip | scp` rather than a registry for the first deployment, the key in a mode-600 env file rather than on the command line, `-p 127.0.0.1:8000:8000` so Docker does not punch its own hole in the host firewall, Caddy for automatic HTTPS in two lines, Lightsail Containers as the alternative with the honest trade-off that the request log does not survive a deployment, and a five-item cost-safety checklist whose first item is the Anthropic spend limit, because that is the only control that cannot be defeated by a bug in this repository.

Rejected: building the index in the image's entrypoint (three minutes per start, and the PDFs would have to ship); `python:3.12-alpine` (onnxruntime and the geospatial wheels want glibc, and the saving is not worth the build failures); a multi-worker CMD (the in-memory cap); and committing a `docker-compose.yml` (one container with four flags does not need an orchestration file, and it would be a third place the environment variables are listed).

Where it cannot, it is repeated in as few places as possible.

Why: this repository's Python is written to be read by someone learning, and CLAUDE.md rule 4 asks for plain readable code. `ruff format` would reflow a few hundred lines across every module in one commit, which would bury the night-4 changes in a diff nobody can review and destroy the deliberate line breaks in the long explanatory docstrings that are most of the teaching value here. Rejected: the default ruff rule set (`E` and `F`), because `E501` line-length would fire on dozens of docstring lines that are wrapped for reading rather than for a column limit, and a lint you routinely ignore is worse than no lint; `--fix --unsafe-fixes`, because an unsafe fix is by definition one that can change behaviour and the whole point of adding a linter on a night with no human watching is to catch mistakes, not make new ones; and adding `B`, `UP` or `ANN`, which are opinions about style this project has already answered in CLAUDE.md.

That reader needs none of the architecture and all of the state — what is built, what a human has actually looked at, what the current numbers are, and what is still open. Spreading that across a 406-line README and a 500-line run report does not work, so it is one page, linked from the README, and its most important section is the one that says **what has been verified by a human and what has not**. ## D-082 · 2026-10-20 · Two providers behind one door, and Groq is the one with a free tier

**Decision.** ZoneWise can now answer through **Groq** as well as Anthropic. `LLM_PROVIDER` in `.env` picks one, `GROQ_API_KEY` holds the key, and `LLM_MODEL` defaults to `openai/gpt-oss-120b` on Groq and stays `claude-haiku-5-5` on Anthropic. The Anthropic adapter is untouched.

**Why.** Limitation 1 of `docs/PROJECT_STATUS.md` has been the largest gap in this project since it started: **there has never been a live LLM answer.** Every path — the citation check, the retry, all four abstention routes, the agent's tool loop — is tested against `FakeLLM` and scripted responses. What was missing was not code, it was a key that costs nothing to use. Groq serves open-weights models on a free tier through an endpoint that speaks the OpenAI chat-completions API, which turns "we need a paid key first" into "we need three lines in `.env`".

**The design: the Anthropic response shape is the internal shape.** This is the decision inside the decision. `GroqLLM` translates in **both** directions, so `app/answer.py` and `app/agent.py` contain no provider branch, no provider import and no change at all:

| Going out | Coming back |
| --- | --- |
| `system` beside the messages -> a `system` message in front | `message.content` -> a text block |
| an assistant turn of blocks -> one message, `tool_use` -> `tool_calls` | `message.tool_calls` -> `tool_use` blocks, arguments JSON-parsed |
| a user turn of `tool_result` blocks -> one `tool` message each | `finish_reason` -> `stop_reason` |
| `input_schema` -> `parameters`, wrapped as a function | `usage.prompt_tokens` -> `usage.input_tokens` |

Order is what makes the tool round trip work: OpenAI requires each `tool` message to follow the assistant message whose call it answers, and Anthropic's layout — an assistant `tool_use` turn, then a user turn of `tool_result` blocks — lands in exactly that order when translated turn by turn. The test for it builds the middle turn with `app/agent.py`'s own `assistant_content()`, so it cannot drift from what the agent really sends.

Rejected: a second answering path for Groq (two copies of the citation check is the fastest way to have one of them be wrong); a provider flag read inside `answer.py` (it would spread to `agent.py`, `api.py` and the tests, and the one-door rule of D-040 is the thing that makes this project testable); and the Groq SDK, because `openai` pointed at `base_url` is Groq's own documented way in and adds no second HTTP client.

**The key check is as strict as D-040's, for the same reason.** A client refuses to be built unless the key starts with `gsk_` and is at least 40 characters. `.env.example` ships `GROQ_API_KEY=your-key-here`, so a copied-but-unedited file would otherwise read as a configured key and turn an honest 503 into a 401 from a call that never had a chance. `has_api_key` is now **provider-aware**: with `LLM_PROVIDER=groq`, an Anthropic key is not a key, so `/api/ask`, the startup banner and the web app cannot disagree about whether answers are possible.

**Three things the Groq adapter has to handle that Anthropic's does not.**

1. **Reasoning text must never reach a user.** `openai/gpt-oss-120b` is a reasoning model and Groq returns its chain of thought in a separate field on the message. `from_openai_response` reads `message.content` and `message.tool_calls` and *nothing else*, so the reasoning cannot reach an answer, a citation, or the JSONL request log — and there is a test asserting that a reply whose reasoning says "I should pretend clause 99 exists" produces an answer with no trace of it. It is sent `reasoning_effort=low`: the answering job is short, extractive and bounded by six retrieved clauses, so the work that matters is reading them, not planning, and reasoning tokens are billed and rate-limited like any others. A model that rejects the setting is retried once without it, so a change at Groq's end degrades rather than breaks.

2. **`max_tokens` means different things on the two APIs.** On Anthropic it bounds the answer. On Groq a reasoning model's hidden thinking is counted in the same completion budget, so passing `answer_max_tokens=900` straight through would let the reasoning eat the answer and truncate it mid-sentence — which the citation check would then reject, turning a provider difference into an abstention that looks like a model failure. So the caller's number keeps its meaning (bound the answer) and the hidden part gets `REASONING_TOKEN_HEADROOM = 1024` of its own. This is the one place a number is changed on the way through, and it is changed in the adapter rather than in `app/config.py` precisely because it is a fact about one API and not a tuning choice. ## D-083 · 2026-10-20 · The fuel-station miss is query expansion, and the fix is written down rather than applied

**The finding is diagnosed.** Limitation 4 of `docs/PROJECT_STATUS.md` — at P_ZONEO, "Can a fuel station be built here?" does not return `MPD47_GAZETTE_EN:11.1.1@p854:0`, the clause saying fuel stations are permitted "in all Use Zones except Recreational ... and Zone O" — is **step 2 of the location path, query expansion**. Rank 14 as shipped, rank 3 with no point at all, **rank 1** with expansion off. Full workings in `reports/diagnosis_fuel_station.md`, regenerable with `scripts/diagnose_fuel_station.py`.

**Exclusion and the boost are both exonerated, by measurement rather than by reading the code.** Turning exclusion off changes the rank by nothing (14 either way), which is what the tags predict: the chunk has `zone_primary: ''` and `zone_mentions: ['zone_o', 'ridge']`, and `should_exclude` acts only on `zone_primary` — the docstring of that function names this very clause as the reason (D-023). Turning the boost off makes it *worse* (14 → 15), and with expansion off the boost lifts the clause from rank 3 to rank 1, so the location path minus one step beats having no location path at all.

**The mechanism is the interesting part, and it is the opposite of the obvious story.** Appending `Zone O Yamuna floodplain` did not make the clause look less like the query. Over all 700 chunks its cosine **rose**, 0.6143 → 0.6519 — it does mention Zone O — while its dense rank **collapsed from 11 to 173**, because about 160 floodplain chunks rose further. A dense query is a single point in embedding space and appending a topic *moves* it; a BM25 query is a bag of tokens and appending a topic *adds* to it. BM25 held the clause at rank 2 in every configuration; the dense index lost it out of a 60-deep pool. Fusion then did exactly what D-028 designed it to do — reward agreement — with one of its two voters answering a different question: `1/(60+2) × 1.5 = 0.0242` for the clause against about `0.0492` for a chunk both indexes like.

**Why it is a Zone O problem rather than a bug in expansion.** The expansion terms are not all the same kind of thing. For `tod`, `hdc`, `land_pooling` and `lda` they are the **heading vocabulary of a chapter**, so moving the dense query towards them moves it towards the right chapter — which is the whole of demo beats 1, 2 and 4. `zone_o` and `ridge` have **no policy section at all** (D-023, D-069), so there is no chapter to aim at and their terms name a *place* instead. The only text about that place is chapter 3.1 Environment, the High Court order and the NGT report — the right answer to "is construction allowed here?" and the wrong answer to any other subject asked in the same place. So: **for a zone with no policy section, query expansion supplies a new subject rather than a qualifier.** It generalises past fuel stations; the same failure should be expected for parking norms or building height at P_ZONEO and P_RIDGE. The two topics that cannot exclude turn out to be the two that cannot safely expand, which is the same asymmetry appearing a second time in a second step.

**Decided: the fix is proposed and not applied.** The proposal is to expand only for the four topics that have a policy section of their own — the same four already allowed to exclude — leaving `zone_o` and `ridge` boosted but not expanded. Measured: the clause goes to **rank 1** under both wordings, with the fuel-station norms chunk at rank 2 behind it, and **three of the five published demo beats come back bit-identical** (beats 1, 2 and 4, whose topics keep their expansion). Not applied, for three reasons in order of weight: there is still no verified question set, and every retrieval change in this project waits on that (D-070, D-071) — two questions at one point is a finding, not evidence; it moves two published demo beats, so `docs/DEMO.md` would need re-running and the beat-3 narrative re-reading, because a High Court order at rank 1 is a different story to tell than an environment clause at rank 1; and the `ridge` half of the fix is justified by the mechanism but measured only on `zone_o`, with no draft question that would test it. When it does ship it should ship as a setting that is off by default and as a fifth configuration in `eval/run_eval.py`, which is exactly how the reranker was handled.

**Three alternatives were measured and rejected, and they fail in the same way.**

| alternative | fuel station | why rejected |
| --- | --- | --- |
| fuse a **third list**, `dense(original)` alongside `dense(expanded)` and `bm25(expanded)` | rank 1 | breaks beats 2 and 4: FAQ chunks `Q5@p15` and `Q18@p16` displace the gazette's `4.3@p757`, putting **authority rank 3 above authority rank 1** |
| the same at **half weight** | rank 8 | the worst of both — the FAQ promotion happens anyway and the clause still never reaches the top 6 |
| expand the **keyword query only** | rank 1 | same FAQ-over-gazette problem, and it discards the dense half of the location effect at every point rather than at the two that need it |

The common failure is worth recording because it is what makes the scoped fix the right *shape*: any change that re-admits the un-expanded dense ranking everywhere re-admits plain semantic search, and plain semantic search over this corpus prefers the FAQ's short conversational chunks to the gazette's clauses. **The expansion is what keeps the gazette on top.** So it should be removed where it has nothing to aim at, not weakened everywhere. Turning expansion off entirely is rejected for the same reason: it would discard the effect that beats 1, 2 and 4 exist to demonstrate.

**One measurement caveat, recorded so nobody re-derives it.** Chroma's HNSW index is approximate, so a *deep* dense rank wobbles between runs — this clause's no-point dense rank came back as 10 and as 11 on two consecutive runs of the same script. Nothing in the diagnosis turns on one place: the effect being measured is a move of about 160 ranks.

**`scripts/diagnose_fuel_station.py` is new and changes nothing.** It runs the real `search()` through the real indexes and turns each location step off on its own by swapping the settings object `app/location.py` looks its knobs up under, so every number comes from the code that ships rather than from a re-implementation of it. The proposed configuration is measured the same way, by removing two keys from `EXPANSION_TERMS` inside a context manager. It writes `reports/diagnosis_fuel_station_tables.md`, makes no network call and is safe to re-run.

## D-084 · 2026-10-20 · Interchanges answer to their bare name, grouped at 300 m — D-081 resolved

**D-081 is resolved.** `Hauz Khas` now resolves from the local gazetteer with no network call, to 28.543813, 77.205876 — the centre of its two platforms. OSM names an interchange **once per line**, so the downloaded list holds `Hauz Khas (Magenta Line)` and `Hauz Khas (Yellow Line)` and no plain `Hauz Khas`, which is the name a person types; against the normalised query `hauz khas` those two score 0.5806 and 0.6000 on difflib's ratio, far below the 0.85 cutoff.

**The rule, and both halves of it matter.** `gazetteer()` adds one entry per group under the bare name when, and only when:

1. the names differ **only** by a parenthesised suffix — `PAREN_SUFFIX` is anchored to the end and does not nest, because the only thing it is meant to catch is OSM's line qualifier; and
2. **every pair** of them is within **300 m** of every other.

All-pairs rather than a chain, deliberately. With single linkage, A 250 m from B and B 250 m from C would merge two points 500 m apart, which is exactly what the radius exists to forbid. There is a test for the chain case.

**A base name whose entries are not all that close gets no entry at all.** This is the conservative half and it is the same call D-073 already makes for an ambiguous fuzzy match: two stations that merely share a base name have not been identified *by* that bare name, and inventing a midpoint between them would be a **wrong** coordinate rather than a missing one. Falling through to Nominatim costs one donated request; a confident point 2 km from where the user meant costs them the answer. Tested with two stations 2.3 km apart sharing a base name: no bare-name key is created and the query reaches Nominatim.

**300 m was checked against the data rather than guessed.** Of the 278 stations, **14** base names carry a parenthesised suffix, every one of them with exactly two platforms, and the spread is nowhere near the limit:

| | | | |
| --- | --- | --- | --- |
| Anand Vihar 41 m | Botanical Garden 55 m | Welcome 105 m | Dwarka - Kakrola 111 m |
| Karkarduma 126 m | Mayur Vihar - I 144 m | Inderlok 150 m | Kirti Nagar 150 m |
| Dilli Haat - INA 177 m | **Hauz Khas 190 m** | Azadpur 208 m | Netaji Subhash Place 228 m |
| Lajpat Nagar 235 m | Rajouri Garden 281 m | | |

Widest real pair **281 m**, narrowest **41 m**, and the nearest thing to a false positive — two genuinely different stations sharing a base name — would be kilometres apart. So no real case sits close to the threshold in either direction, which is the property that makes a hard cutoff safe here rather than a tuning parameter waiting for evidence.

**The three objections D-081 raised are each answered, which is why this is now a fix and not the same idea again.**

- *"Lower the cutoff"* — not done. The cutoff is untouched at 0.85, and the fuzzy matcher is unchanged. The bare name is an **exact key**, so `Dwarka Sector 21` still cannot match `Dwarka Sector 12`.
- *"Strip the suffix in `build_gazetteer.py`, and the loader keeps whichever it saw first"* — that was the real objection, and it is why the grouping lives in the **loader** rather than in the build script. A group entry carries the **centre** of its members, which needs all of them at once; `key not in found` can only keep one. It also means nobody has to re-download: the change applies to the file already on disk.
- *"It needs a rule for what an interchange is, and a decision about which coordinate the shared name gets"* — those are precisely the two things above: the rule is "same base name and all pairs within 300 m", and the coordinate is the mean of the members. Both are stated, both are tested, and the second is reported through its own path so it can be told apart from an ordinary hit.

**Three properties kept on purpose.**

- **Each platform still answers under its own full name, to its own coordinate.** The group is an extra entry, not a replacement, and it reports `gazetteer` where a group reports `gazetteer_interchange`.
- **A name OSM really holds is never overwritten.** Group entries are added **last** and only when the key is free. This is not hypothetical: OSM holds `Botanical Garden` *and* `Botanical Garden (Blue Line)` *and* `Botanical Garden (Magenta Line)`, so a computed centre would otherwise displace a coordinate the source actually carries. It does not.
- **A new path, `gazetteer_interchange`.** D-073's reason for recording which step answered was that a surprise should be diagnosable from the cache alone. A computed centre is exactly the kind of answer someone will want to query later, so it says so, and each group entry keeps an `interchange_of` list naming the platforms it was built from.

**One behaviour change worth stating plainly: the answer moved 692 m.** Night 3's Nominatim lookup for "Hauz Khas" returned 28.54981, 77.20776 — the Hauz Khas **locality**. The gazetteer now returns the metro **interchange**. Both are defensible readings of the two words; for ZoneWise the interchange is the one a question about building "near Hauz Khas metro" means, and the gazetteer is a metro-station list, so answering with the station is the honest behaviour of the thing being asked. **It changes no answer here** — the centre, both platforms and Nominatim's own point are all in planning zone F and all in a TOD zone — but 690 m can cross a zone boundary somewhere else, and in this project a zone boundary decides which clauses can apply. Hence the separate path.

**A haversine, not a projection.** `metres_between` is ten lines of trigonometry. `app/spatial.py` buffers in EPSG:32643 because a buffer is a geometry and has to be right (D-032); this is a straight-line comparison between two points a few hundred metres apart, where a haversine is accurate to well under a metre and needs neither a projection nor a GeoPandas round trip for 278 stations at import time. Rejected: pyproj in `app/geocode.py`, which would make the geocoder depend on the geo stack for one distance; and comparing degrees directly, which is wrong by a factor of 0.88 in longitude at Delhi's latitude and would have made the threshold mean two different things in the two axes.

Covered: `Hauz Khas` resolving with no request, and under "Hauz Khas metro station", "near Hauz Khas" and "hauz khas, new delhi"; each platform still answering under its own name and path; two stations 2.3 km apart **not** merged and falling through to Nominatim; the three-platform chain case refused; `Botanical Garden`'s real entry surviving; one suffixed entry on its own not grouped; an unsuffixed list gaining nothing; a record with no coordinates skipped rather than raising; `base_name` and `metres_between` on their own; and `all_within` on the empty and single cases. ## D-085 · 2026-10-20 · The first real-model run: how it is paced, resumed, and read

**The gap this closes.** Since day 1 the honest statement in `docs/PROJECT_STATUS.md` has been that **there has never been a live LLM answer**: every path — the citation check, the single retry, all four abstention routes, the agent's tool loop — was tested against `FakeLLM` and scripted replies (D-040). `scripts/live_run.py` produces the first real ones. It is a **recording, not a review**: it changes no prompt, no threshold and no retrieval setting, and nothing in it reacts to what the model says. `reports/live_answers_v1.md` carries that in a banner at the top, because a file full of real answers is exactly the kind of artefact a future reader would otherwise mistake for an evaluation.

**Resumable, because a free tier runs out.** Every finished case is appended to `reports/live_run_state.json` and the whole report is **rewritten from that file** after each one. Two consequences, both deliberate: a run that stops halfway leaves a readable report rather than a truncated one, and `--resume` continues at the next case — the next day, after the daily token limit resets, if that is what it takes. The report is a pure function of the state file, so there is no way for the two to drift. Rejected: appending to the report as the run goes (a crash mid-write leaves broken markdown, and the summary at the top cannot be written until the end), and keeping the records in memory until the end (which is the one design that loses everything when the quota runs out).

A plain run over an existing partial state **refuses to start** and prints the two ways forward, `--resume` or `--restart`. The alternative — a bare `live_run.py` silently discarding yesterday's 30 cases — is the kind of data loss that is obvious only after it happens.

**Two caps, and neither is a cost control.** Groq's free tier is the cost control. `LIVE_TOKEN_BUDGET` (default 150,000, checked before each case) and a hard cap of 120 LLM calls are there so that an unattended run cannot spend a day's quota on a bug — a retry loop, a prompt that never terminates, an agent that tool-calls forever. Hitting either is a **clean stop** with `stopped_because` recorded, not an error: the report says which cap it was and how to continue.

**`LLM_MIN_INTERVAL_S=2.5` for this run**, set in the script before `app.config` is imported so `settings` reports the value actually used, and overridable with `--interval`. 2.5 s is 24 requests a minute against the free tier's 30. **The requests-per-minute limit turned out not to be the binding one**: the headers say `x-ratelimit-limit-tokens: 8000`, which is 8,000 tokens a *minute*, and a map-mode case costs about 5-6k tokens. So the real pace is set by the token bucket and by the retry machinery absorbing its 429s (D-082), which is precisely why the report counts 429s and rate-limit waits as first-class numbers rather than hiding them.

**A draft question with no point goes through the agent, and no new code was written for it.** 15 of the 30 sampled drafts — every `general` one and five `abstain` ones — have `lat: null`. `answer_point` needs a point and `/api/ask` requires `lat` and `lon` in its request model, so the **shipped** route for a question without one is `/api/agent` and `run_agent`, which exists for exactly that case. The alternative was to factor a no-point answering function out of `app/answer.py`, and that is a change to the answering path made in order to measure the answering path, on a night with instructions to change no code in reaction to results. So: a point means map mode, no point means agent mode, each case records which, and the report says so. The cost is that the two modes are not comparable on tokens or latency — an agent case replays its context every round — and that is stated rather than averaged away.

**Thirty drafts, seed 11, and they are read rather than scored.** 10 `location`, 10 `general`, and all 10 `abstain`, sampled from an id-sorted pool with `random.Random(11)` so the same thirty come back on every machine and a resumed run continues the same list. The report says in its own words that this is **not a measurement**: the drafts are `verified: false` and were written by Claude from the chunks, which is the one setup that flatters retrieval (D-054). What thirty real answers are good for is noticing what is wrong with them, which no retrieval metric can do. The `expected_chunk_ids` are still recorded per case, and the distinction that matters is kept: whether the expected clause was **cited**, and if not, whether it was **retrieved and then not cited** — those are a retrieval problem and an answering problem respectively, and lumping them together would hide which one to work on.

**The suspected-problem list is mechanical on purpose.** Each rule is a few lines that either fire or do not: abstained on a question the demo says is answerable; answered a should-abstain question; the citation check failed twice; needed a citation retry; longer than the 200 words prompt rule 7 asks for; cited **only** the FAQ although a gazette clause was retrieved; the agent placed the location further from the named place than the case's tolerance; the agent answered without ever establishing a point; the expected clause was retrieved but not cited. A rule a script can apply is a rule a human can check, and the point of the run is to hand a person a shortlist, not a verdict. The expected outcome per demo case is the only opinion in the file and it is taken from `docs/DEMO.md` rather than invented: "answer" where the demo prints clause ids it is happy with, "abstain" where the demo says the answering layer should decline, and "either" where the demo itself records that the retrieval is wrong, so both outcomes are defensible.

The five agent cases each carry an approximate coordinate and a generous radius, because the question being asked is "did it land in the right part of Delhi", not "is it accurate to the metre". Two of the five go through the gazetteer and one of those is an interchange, which makes them the first live exercise of D-084.

## D-086 · 2026-10-20 · Query expansion only where there is a policy section to expand towards
`app/location.py` gains one tuple, `EXPANDS_QUERY = ("tod", "hdc", "land_pooling", "lda")`, and `expand_query` skips every topic outside it. A point in **Zone O** or on the **Ridge** is still boosted and is still never excluded, but its zone words are no longer appended to the query. This applies the fix D-083 wrote down and deliberately did not apply; the lead reviewed the diagnosis and decided to ship it.

**Why.** The two topics with no policy section are the two whose expansion terms name a *place* rather than a *policy*. A BM25 query is a bag of tokens and appending a topic **adds** to it; a dense query is one point in embedding space and appending a topic **moves** it. For `tod`, `hdc`, `land_pooling` and `lda` that move is towards a real chapter — which is what `docs/DEMO.md` beats 1, 2 and 4 exist to show. For `zone_o` and `ridge` there is no chapter to move towards, so the move lands on whatever text in the corpus is *about the floodplain* or *about the Ridge*, and the question's own subject is half replaced. The measured case: at P_ZONEO, "Can a fuel station be built here?" put `MPD47_GAZETTE_EN:11.1.1@p854:0` — the clause that says fuel stations are permitted "in all Use Zones except Recreational … and Zone O" — at **rank 14**, while that clause's own dense cosine *rose* from 0.6143 to 0.6519 and its dense rank collapsed from 11 to 173 of 700, because about 160 floodplain chunks rose further. It is now **rank 1**, under both wordings, with the fuel-station norms chunk at rank 2 behind it. Full diagnosis in `reports/diagnosis_fuel_station.md`.

**It is the same asymmetry as exclusion, which is the argument for the shape of the fix.** `should_exclude` acts only on `zone_primary`, and `zone_o` and `ridge` have no `zone_primary` anywhere in the corpus (D-023, D-037, D-069), so exclusion already has nothing to find for them. One cause — no policy section — now disables two of the three steps for the same two topics. The boost is untouched and is doing real work: with expansion off, the boost lifts the fuel-station clause from rank 3, where no point at all puts it, to rank 1.

**Three of the five published demo beats come back bit-identical**, which is the test that mattered: beats 1 (P_TOD), 2 (P_HDC) and 4 (P_LDA) keep their expansion and did not move a single chunk id. `reports/location_compare_v4.md` makes the same check at nine points across five questions and **2 of 9 changed** — P_ZONEO and P_RIDGE.

**What it cost, which is recorded rather than buried.** The mechanism cuts both ways. Expansion was *helping* whenever the question's own subject **was** the place, because then the appended words were a qualifier after all, and those questions now do worse:

**A better option exists, is measured, and is not applied.** Fuse **four** lists instead of two, scoped to `zone_o` and `ridge` only: `dense(plain)`, `bm25(plain)`, `dense(expanded)`, `bm25(expanded)`. On the six questions above it keeps every win and gives back every loss: the fuel-station clause stays at rank 1, `3.1.2@p681` returns to rank 2 for "Can I construct a building here?" and `10.1@p842` returns to rank 1 at P_RIDGE. The vocabulary for both topics stays in `EXPANSION_TERMS`, so widening the scope back is one tuple and not a re-derivation. The rejected attempt and its problems list were never written anywhere — not in the state file, and not in `data/logs/requests.jsonl`, which only sees calls that came through `app/api.py`. Recording a number without its breakdown is the kind of thing that is cheap to fix once and expensive to re-run, so two things were done.

**`AnswerResult` gains `validation_failures`**: a list with one problems list per rejected attempt, filled by both `answer_point` and the agent. It holds **only the strings this repository generated**, never the rejected answer text, which matters because `AnswerResult.to_dict()` is what the API returns and the request log stores — un-validated model prose must not leave through a field added for diagnostics. ## D-088 · 2026-10-20 · Map mode answers in JSON, and validation becomes structural
The model no longer writes prose with `[C#]` markers in it. It returns one JSON object:

```json
{"abstain": null, "sentences": [{"text": "...", "citations": ["C1", "C3"]}]}
```

and `answer_markdown` is **rendered** from those sentences with the same markers in the same places, so `/api/ask`, the frontend, the clause drawer and the citations table are untouched. A client cannot tell the difference; a test asserts that by checking the rendered output against the pre-D-088 prose constant.

**Why.** Against a real model, **18 of the 22 map-mode answers that reached the citation check failed on the first attempt** — a first-attempt pass rate of 18% (D-087). The check was reading prose: it split the answer into sentences with a regular expression and required a marker in each. That put a convention about where to put square brackets between the model and a shown answer, and the convention loses to ordinary writing — a thought spanning two sentences, a bullet, a parenthetical, a heading. A JSON array has no splitter to disagree with, because a sentence and its sources are **one record**. The pairing is the data structure instead of a habit.

**Validation is now three structural checks.** The reply parses as a JSON object; `sentences` is a non-empty list of objects each with usable `text`; every sentence has at least one citation; every citation names a label that was issued. Each problem names the sentence it is about and quotes the first 120 characters of it, because a retry is only as good as what it is told (D-044). One retry with the faults listed, then `citation_check_failed` with the clauses still returned — every existing abstention reason and route is unchanged.

**Groq's JSON mode is used, and is treated as a request rather than a contract.** `chat()` gains `json_object: bool`, which `GroqLLM` sends as `response_format={"type": "json_object"}`. Three deliberate limits. It is **not sent alongside tools**, because a tool call is itself a structured reply and the agent's final answer has to be reachable from a conversation that still carries tool definitions — the agent gets its JSON from the prompt instead (D-089). `AnthropicLLM` **ignores** the flag, because the Messages API has no `response_format` at all, so that provider gets the contract through the prompt. And a model that refuses the parameter is retried once without it and remembered as refusing, so it costs one call per run rather than one per question — the same handling `reasoning_effort` already had, generalised.

**So parsing is forgiving about the wrapper and strict about the contents.** `strip_code_fences` removes a ```json fence, which models add however firmly they are told not to; failing that, the object is recovered from the first `{` to the last `}`; a reply that is not JSON at all is a named problem that goes into the retry. `clean_label` accepts `"C1"`, `"[C1]"`, `" c1 "` and normalises them, because the letter and the number both have to survive and the result is still checked against the labels actually issued — tolerance that cannot admit an invented source. A model that ignores the contract entirely and replies `ABSTAIN: ...` is **still honoured**: it has answered the only question that matters, and retrying it for format would spend a call to reach the same end.

**One prompt rule added, and every existing one kept.** Rule 8 is new, verbatim: *"Each sentence must be stated by its cited clause. Do not combine clauses to reach a conclusion that none of them states. If no clause answers the question directly, abstain."* It exists because of `demo-07` (D-085), where 134 confident words concluded that construction was prohibited on the Ridge out of a Regional Park definition, a park built-up ceiling and a drain-buffer rule — every sentence correctly cited, and no clause saying what the answer said. Rules 1 and 4 to 6 are unchanged word for word. Rules 2, 3 and 7 keep their substance and are re-expressed for the new format, because they described the prose: rule 2's "end every sentence with a marker" is now "every sentence must list at least one source in its citations", rule 3's `ABSTAIN:` line is now the `abstain` field, and rule 7 drops "short bullet points" since a bullet is now a sentence entry.

**What this does not fix, stated here because the 18% makes it tempting to think otherwise.** Nothing structural can tell whether a cited clause *supports* its sentence. Rule 8 asks for that in words and the check cannot verify it. The sharpest evidence is in `reports/citation_failures_v1.md`: **prompt rules 2 and 6 contradict each other** — rule 6 asks the model to say official DDA documents should be checked, which no clause states, while rule 2 demands a citation on every sentence — and **7 of the 17 v1 answers carry that sentence with a marker bolted on**. Both rules were kept, as instructed, so that defect is unchanged by this entry and is **recorded rather than fixed**. It is the first prompt change to make once a human has read answers, and the shape of the fix is already visible: the caveat belongs in the interface, not in a cited sentence.

**`AnswerResult.validation_failures`** carries one problems list per rejected attempt (D-087). It holds only strings this repository generated, never the rejected answer text, because that field is returned by the API and written to the request log.

**14 new tests, 461 pass.** Covered, as asked: good JSON; broken JSON retried and fixed, with the fault named; an empty citations list, twice, abstaining; an unknown citation retried then succeeding, with the rejected attempt's faults kept; an abstain object with its reason; and code-fenced JSON. Plus the unit layer — label normalisation refusing `"clause 4.2.3"`, fences in three shapes, an object recovered from prose around it, `abstain` read only when it holds a reason, structural problems naming sentence 2 of 4, rendering putting markers before the full stop and deduplicating them — and Groq's JSON mode being sent, never sent with tools, retried without it on refusal and not asked for again.

Rejected: a JSON **schema** through Groq's structured-outputs mode rather than plain `json_object` (it is model-specific, it would not work on Anthropic at all, and three checks in our own code are easier to read and to test than a schema that two providers interpret differently); keeping the prose check as a second gate on the rendered markdown (two validators, and the second can only fail when our own renderer is broken — which a test covers instead); and returning the sentence array in the API response next to the markdown (nothing needs it, and the citations list already gives a client the structure).

## D-090 · 2026-10-20 · A fifth geocoding step: the contiguous sub-phrases of a failed query
When the whole query matches neither the gazetteer nor Nominatim, `locate_place` breaks it into **every contiguous run of up to three words, longest first**, tries all of them against the local gazetteer, and then asks Nominatim about **one** — the longest. `Place.matched` reports which part answered, and is `None` whenever the whole query did, which is the normal case.

**Why.** `agent-05` was asked "Is construction allowed in the Ridge near Chhatarpur?" and called `locate_place("Chhatarpur ridge")` — the landmark plus the question's own subject. That misses twice over: `chhatarpur ridge` scores 0.63 against `chhatarpur` on difflib's ratio, under the 0.85 cutoff, and bounded Nominatim has nothing for the phrase. `"Chhatarpur"` alone resolves from the gazetteer instantly, so the agent abstained with "location not found in Delhi" one tool call into a question the data could answer (D-085). The agent's prompt was fixed too (D-089), and the two fixes are deliberately independent: a better prompt does not help a user who types the compound phrase into the box themselves, and a better geocoder does not stop the agent wasting a round.

**Contiguous runs, not combinations.** A place name is a phrase. Recombining words out of order would invent candidates the user never wrote, and three words is the cap because it covers "dwarka sector 21" and "new friends colony" while keeping the candidate list short — six words yield fifteen candidates, and all but one are answered locally at no cost.

**The request budget is the part that needed deciding**, because Nominatim is donated capacity and the policy is one request a second (D-046). The gazetteer is asked about every candidate, because it is local and instant. Nominatim is asked about exactly one, so the worst case for a single unknown query goes from two requests to **three**, and a query the gazetteer can answer at any stage still costs none. The existing limiter and cache are untouched: the fallback goes through `ask_nominatim` like everything else, and the result is cached under the original query, `matched` included, so the second call is free and a miss stays diagnosable from the cache alone.

**Which sub-phrase gets the one request, and the honest limit of that choice.** The longest, because it is the most specific thing the user actually wrote and the shorter candidates are fragments of it. That is not always the right pick: for "yamuna floodplain near ito" with no gazetteer present, the request goes to "yamuna floodplain" and not to "ito". With the gazetteer present — which is the shipped configuration — that query resolves to ITO at no cost, because the gazetteer sweep reaches every candidate. The limit is recorded rather than hidden, and `Place.matched` is what makes it visible: it names the part that answered, so an answer about the wrong half of a compound question can be seen in the tool trace instead of being inferred later.

**A timeout or a 500 skips the fallback.** A service that has just failed says nothing about the name, so spending one more request on it would be the same mistake D-073 already decided against for the second whole-query attempt.

**9 new tests, 474 pass, and none touches the network.** Covered, as asked: "chhatarpur ridge" resolving to Chhatarpur with `path=subphrase_gazetteer` and `matched="chhatarpur"`; "yamuna floodplain near ito" resolving to ITO; and a phrase with no real place in it still coming back `not_found` after exactly three requests, because a fallback that turns "no" into a point somewhere would be far worse than the miss it replaces. Plus `subphrases` being contiguous, longest first, capped at three words and empty for an empty string; the longest sub-phrase being the one Nominatim is asked about; a timeout skipping the fallback; `matched` surviving the cache; and a clean whole-query match never being pre-empted.

Rejected: asking Nominatim about every sub-phrase (fifteen requests for a six-word query, against a donated service, to answer one question); dropping stop words and recombining the rest (invents phrases the user did not write, and "sector 21" would lose "21" to any list that counts it a stop word); and running the fallback before Nominatim rather than after (a two-word place name would then be answered by one of its halves, and "Hauz Khas" would resolve to "Hauz").

## D-092 · 2026-10-20 · The caveat is a field, not a sentence: the rule 2 / rule 6 contradiction is resolved
**Decision.** The model is no longer asked to write a caveat. Prompt rule 6 in both `app/answer.py` and `app/agent.py` now reads "Do not give legal advice. Describe only what the documents say. Do not add a caveat, a disclaimer or a sentence telling the reader to check anything: one is added outside your answer." In its place `AnswerResult` carries a fixed field, `disclaimer`, set by code to one string — **"Not legal advice. Check the official MPD-2047 text and DDA before acting."** — on every answer *and* every refusal. The API returns it; `web/src/components/AnswerPanel.jsx` renders it under the answer in muted type above the latency line.

**Why.** This closes the sharpest defect this project has recorded about itself. `reports/citation_failures_v1.md` found that **prompt rules 2 and 6 contradicted each other**: rule 6 told the model to say that official DDA documents should be checked, no clause in the corpus says that, and rule 2 demanded a citation on every sentence. The only way to obey both was to attach a marker to a sentence the clause does not support — and **7 of v1's 17 shown answers did exactly that**, with `[C1]` or `[C5]` bolted onto "Official DDA documents should be checked…". The structural check passes it by construction, because it verifies that a marker is *present* and *valid* and never that the clause *says* the sentence. So the prompt was instructing the model to produce the one defect the check cannot see, on roughly two answers in five. D-085 and D-088 both recorded this and left it, as instructed; the lead has now decided it.

**The shape of the fix is the point.** A caveat is a statement about *the product*, not about the Master Plan, so no clause can ever support it and no citation can ever be honest. It therefore does not belong in a cited sentence, and the right place for it is the layer that knows it is true: code. The field is outside `sentences`, so `structural_problems` never sees it, `render_markdown` never writes it, and the citation count is unaffected. A test asserts that the string is **not** in `answer_markdown`, which is the assertion that keeps the two layers apart.

**It is on refusals too.** A refusal still tells a user something about Delhi planning law — "no clause here says you may not build" is information somebody could act on — so it carries the same caveat. The UI renders the field whenever it is present, which covers both branches without a second rule.

**The string is never shown to the model**, asserted by a test. If it were in the system prompt, a model asked not to write a caveat would have been handed the exact words of one.

Rejected: keeping rule 6 and accepting the defect (two more runs of it are already recorded, and the next run is the last before the freeze); putting the caveat in the frontend only (then an API consumer gets answers with no caveat at all, and the field is one line); making it configurable (it is a legal notice, not a tuning knob); and asking the model for a caveat and then *exempting* it from rule 2 (that re-admits an unsourced sentence into the validated list, which is exactly what the citation check exists to prevent).

**Four new tests, 481 pass.** Covered: the field is the fixed string on an answer; it is on a refusal (`outside_delhi`) as well; it is absent from `answer_markdown`; the prompt no longer contains "official DDA documents should be checked" and does contain "Do not add a caveat"; the no-legal-advice half of rule 6 survives; the disclaimer string is not in the system prompt; the agent's prompt and result got the same treatment; and `/api/ask` returns the field. The `GOOD_SENTENCES` fixture in `tests/test_answer.py` no longer models the model writing a caveat, because the prompt now forbids one.

## D-093 · 2026-10-20 · The scoped four-list fusion ships: both wordings vote instead of one replacing the other
**Decision.** `app/location.py` gains a second module constant, `FUSES_FOUR_LISTS = ("zone_o", "ridge")`, and a function `place_query`. For a point in Zone O or on the Ridge the search now sends **two** queries — the user's words (plus any policy-zone expansion) and the same words with the place terms appended — and fuses **four** ranked lists into one RRF: `dense(plain)`, `bm25(plain)`, `dense(expanded)`, `bm25(expanded)`. Exclusion and the boost are untouched. The previous behaviour is kept scoreable as a fifth evaluation configuration, `hybrid+location_v2`, in `eval/run_eval.py`. This applies the fifth option D-086 measured and deliberately left on the shelf; the lead reviewed it and decided to ship it.

**Why.** D-086 had to choose between two kinds of question at the same point, and it said so: appending `Zone O Yamuna floodplain` to the only query **replaces** the subject of a question whose subject is something else, which is why the fuel-station clause sat at rank 14; removing it **loses** the questions whose subject *is* the place, which is why `3.1.2@p681` fell from rank 1 to outside a 200-deep list for "Can I construct a building here?". Fusion does not have to choose. RRF adds `1/(k + rank)` over the lists a chunk appears in, so a clause only needs **one** of the two wordings to find it in order to earn points — and a clause both wordings find beats one that only a single list ranks highly, which is the property k = 60 was chosen for in the first place (D-028).

**Measured, as shipped, in `reports/location_compare_v5.md`.** The two questions the lead named both keep their clause:

| point | question | clause | before D-086 | two lists (D-086) | four lists |
| --- | --- | --- | --- | --- | --- |
| P_ZONEO | Can a fuel station be built here? | `11.1.1@p854` | 14 | **1** | **1** |
| P_ZONEO | Can I construct a building here? | `3.1.2@p681` | 1 | >200 | **2** |
| P_ZONEO | Can I construct a building here? | `DHC…:2` | 2 | 9 | **1** |
| P_RIDGE | Can I build a house here? | `10.1@p842` | 1 | >200 | **1** |

These reproduce D-086's own four-list measurement exactly, which is worth saying: the numbers in that entry were taken ad hoc and have now been produced by the shipped code path and written to a committed report.

**Scoping is the whole safety argument, and it is structural rather than empirical.** `reports/location_compare_v5.md` is a three-column table — before D-086, two lists, four lists — at nine points across five questions, and **2 of 9 changed**: P_ZONEO and P_RIDGE. The other seven are byte-identical in all three columns, and they have to be, because a point with no `zone_o` or `ridge` topic never reaches the second query at all. That is what distinguishes this from the third-list variant D-083 measured and rejected: re-admitting the un-expanded dense ranking at **every** point re-admits plain semantic search, and plain semantic search over this corpus likes the FAQ's short conversational chunks — it put `Q5@p15` and `Q18@p16` above the gazette's `4.3@p757`, which is **authority rank 3 above authority rank 1**, and broke demo beats 1, 2 and 4. The scoped version cannot do that, by construction. A test asserts the scope rather than describing it: `set(FUSES_FOUR_LISTS) == set(TOPICS) - set(EXPANDS_QUERY)`.

**So the three location steps now line up on one fact about the corpus.** MPD-2047 has no Zone O chapter and no Ridge chapter. The four topics that *do* have a policy section exclude, expand their single query, and fuse two lists. The two that do not never exclude (D-023, D-037, D-069), never expand the single query (D-086), and instead fuse four lists so their place words are an **extra vote** rather than a replacement. One cause, three steps, and the asymmetry is the same shape each time.

**What it costs.** A second embedding call and a second BM25 pass, for points in Zone O or the Ridge only. That was one of D-086's three reasons for not applying it, and it is accepted now because the alternative is a measured wrong answer at those points: "Can I construct a building here?" in the Yamuna floodplain currently comes back with chapter 13 utilities and a slum FAQ. The score breakdown is **first-pair-first** — a chunk the original pair found keeps exactly the `dense_rank`, `dense_cosine` and `bm25_score` it had before, so the abstention pre-check reads the same number for it as it always did (D-071); a chunk only the second pair found reports that pair's numbers, because the alternative is showing a result with no numbers at all. The reranker, when on, reads the fullest query, since with four lists there is no single text every pool saw; it is off by default (D-070) so nothing exercises that choice either way.

**Not a setting, for D-086's reason.** It is a module constant, like `EXPANDS_QUERY`, because it is a statement about the corpus rather than a knob. `eval/run_eval.py` therefore scores the old behaviour by emptying the tuple for the length of one call — a `four_list_fusion(on)` context manager beside the existing `reranker(on)` one — which is the same technique `scripts/day3_location_compare.py` already used to reproduce the pre-D-086 behaviour.

Rejected: fusing four lists at every point (measured, breaks three demo beats, puts the FAQ above the gazette); weighting the plain lists at half (measured in D-083: the FAQ promotion happens anyway and the fuel-station clause reaches only rank 8); a flag defaulting to off (then the shipped product is not the measured one); and waiting for `eval/questions_verified.jsonl`, which is the right default for a retrieval change and is overridden here for D-086's reason — the failure being fixed is a mechanism that generalises past one question, and this is the last change before the freeze.

**Seven new tests, 488 pass.** Covered: `place_query` appending Zone O's words, returning a TOD-only query untouched, and building on **top** of the TOD expansion for a point in both; the scope assertion above; a Zone O point fusing four lists and keeping a clause only the place query could find, with the chunk three of the four lists agree on ranked first; a policy-zone point still sending one query and fusing two, which is the demo-beat guarantee as an assertion; and the first-pair-first score breakdown, which matters because `dense_cosine` is what the abstention guard reads.

## D-094 · 2026-10-20 · A deterministic note when the question names a zone the point is not in
**Decision.** Both answering paths now build a `location_note` in code and return it as its own field. The rule: take the zone topics the **question's own words** name, using `app.tagging`'s mention regexes through a new `named_zone_topics`; drop the ones the point is actually in; and for each one that is left, measure the distance from the point to the nearest polygon of that zone in EPSG:32643 and write one sentence —

> This point is not inside Zone O (Yamuna floodplain) on DDA's map; the nearest Zone O boundary is about 600 m away.

The API returns it (`AnswerResult.location_note`, and a line in `data/logs/requests.jsonl`), the interface shows it **above** the answer, and the model is given it as context with the instruction to answer for the located point or abstain, not for the zone the question named. It is `""` for almost every question, which is the point.

**Why.** v2's `agent-02` is the case. "Can I build a house on the Yamuna floodplain near ITO?" came back with the floodplain's no-construction clause, correctly quoted and correctly cited — about a point `get_zones` says is in a TOD zone, 620 m from the nearest Zone O polygon. `docs/PROJECT_STATUS.md` called it "a regression dressed as a win", and it is the clearest example of a failure no part of this system could previously see. Retrieval worked *because* the question said "floodplain", so the words did their job; the citation check passed because the clause really does say what the sentence says; and v1, which abstained there, looked worse. Nothing was broken except the match between the question and the place.

**It is a mismatch, not an error, which is why the answer is not blocked.** A user who clicks near ITO and asks about the floodplain may want either answer: what applies *here*, or what the floodplain rules say. Refusing would throw away a good retrieval; answering silently would describe somewhere else. Naming the gap and handing it to both the reader and the model is the only option that loses nothing. The model is told to answer for the point; if the sources do not cover the point, rule 3 already tells it to abstain.

**The note is code, for the same reason the disclaimer is (D-092).** Nothing in MPD-2047 states how far a point is from Zone O, so no clause can support that sentence and no citation for it could be honest. It is therefore built from `get_zones` and DDA's own layers, lives outside `sentences`, is never seen by `structural_problems`, and is asserted by a test to be absent from `answer_markdown`. Two sources of truth in one answer, each labelled: the model's cited sentences, and the system's own facts.

**How the distance is measured.** A new `app/spatial.py` half: `TOPIC_LAYERS` maps each topic to its layer, `metric_shapes` projects that layer's polygons into EPSG:32643 once and keeps an STRtree over them, and `distance_to_topic` projects the point and asks the tree. `zone_o` has no layer of its own — it *is* planning zone "O" — so the planning_zones layer is filtered on `zone_name`, exactly as `get_zones` does it, and a test checks that the filter kept one polygon rather than all sixteen. It returns `0.0` inside a zone, so it is a distance and not a "how far outside", and `None` rather than an exception when a topic has no polygons, in which case the note drops its distance clause and keeps its first half. Caching is keyed by the same folder string `load_layers` is keyed by: 10 ms to project the 208 low density area polygons the first time, 0.15 ms after.

**Rounded hard, on purpose.** "about 600 m", "about 1.1 km", "less than 50 m" — metres to the nearest 50, kilometres to one decimal. The layers are DDA's published shapes, and a note that said "613 m" would claim a survey accuracy nothing in this repository has.

**One sentence per zone, in `TOPICS` order**, so a question naming three zones the point is outside gets three sentences in a fixed order and the string is reproducible. The zone the point *is* in is never mentioned, even when the question names it.

**In the agent, the note travels in the tool result.** `get_zones` and a located `search_clauses` both attach `location_note` and an `answer_for` instruction, and `remember_note` recomputes it whenever a tool establishes a point — so an agent that locates a second place gets the second place's note. It is in the tool trace as well, so a reader of `reports/live_answers_v3.md` can see why an answer is hedged. `AgentRun` now keeps the question, because the tools only ever see a place name or a search query and the note is built from the question's own words.

Rejected: blocking the answer on a mismatch (throws away a good retrieval, and `agent-02` is a question with two defensible answers); asking the *model* to notice the mismatch (it is arithmetic over polygons, and a model that could be trusted to notice would not have needed telling); putting the note in the system prompt (it is per-question data, not a rule); a boolean "zone mismatch" flag with no distance (1 m and 10 km are the same `false` and only one of them makes the answer wrong); and using `app.geocode.metres_between`'s haversine instead of a projection (that measures between two points, and the nearest *polygon* needs a projected geometry — CLAUDE.md pins EPSG:32643 for exactly this).

**Twenty new tests, 508 pass.** Covered: the `agent-02` case end to end, with the note in the `get_zones` tool result, in the trace and on the result, and absent from the answer text; a located `search_clauses` with no `get_zones` call getting it too; a matching zone adding nothing at all to the tool result; a question naming three zones getting three sentences in `TOPICS` order with the point's own zone unmentioned; "bridge" not matching `ridge`; a point outside Delhi getting no note; a note keeping its first half when the distance is unavailable; the rounding at five distances; `distance_to_topic` returning 0.0 inside, a real distance outside, `None` for an unknown topic, and measuring `zone_o` off the filtered planning_zones layer; and both label maps covering all six topics, because a missing one would be a `KeyError` mid-answer.

## D-095 · 2026-10-20 · One cited sentence per rule, with the clause's own figures
**Decision.** Both prompts gain one rule — rule 9 in `app/answer.py`, rule 10 in `app/agent.py`, appended so the existing numbers that reports and docs quote do not shift:

> When several of the sources are relevant, give each relevant rule as its own cited sentence, up to six sentences. Include the specific figures the clause gives: FAR, ground coverage, height, setbacks, minimum plot size. A figure must come from the clause you cite for that sentence.

Rule 8 (map) and rule 9 (agent), the no-synthesis rule, are **unchanged**, and rule 7's 200-word limit still applies as the outer bound.

**Why.** v2's answers came back much shorter than v1's: median **42 words against 116**, median **1 citation against 2** (D-091). `docs/PROJECT_STATUS.md` lists this as something only a reader can judge, and that is still true — but the two candidate explanations have different fixes, and one of them is a prompt rule. If the shortening is rule 8 removing padding v1 could not support, the answers are better and nothing should change. If it is the model answering the narrowest readable version of the question and dropping the plot-size figure a user came for, the fix is to ask. D-088 replaced prose with a JSON array of sentences, and a model given an array and no instruction about how many to fill has every reason to send one.

**The rule asks for more clauses quoted, never more inference.** That distinction is the whole of it, and it is why the two rules have to be read together: "give each relevant rule its own sentence" **plus** "each sentence must be stated by its cited clause" is an instruction to cite more of what was retrieved; the first without the second would be an invitation to pad, which is precisely what v1 did and what rule 8 exists to stop. The figures clause tightens it further by naming what a fuller answer should be fuller *with* — FAR, ground coverage, height, setbacks, plot size, the five numbers a planning question is usually about — and by requiring the figure to come from the sentence's own cited clause. A single test asserts both rules at once, because the new one only means what it is supposed to mean while the old one is still there.

**Six, and not more.** Six is the number of sources map mode supplies (`settings.default_k`), so "one sentence per relevant rule" cannot exceed it, and six sentences at the project's observed sentence length sits comfortably under rule 7's 200 words. It is a cap on an instruction to write *more*, which is the only direction this rule pushes.

**Measured in v3 and not tuned on.** `reports/live_answers_v3.md` reports median words and median citations per case against v1 and v2. Whether this rule helped is a judgement about answer quality, which this project has never been able to make mechanically and will not pretend to now: the run records, a person reads. Nothing in v3 was changed in response to v3.

Rejected: raising the word limit in rule 7 instead (a limit is not an instruction — the model was already well inside it at 42 words, so a higher ceiling changes nothing); asking for a fixed number of sentences (an answerable question with one applicable clause should get one sentence, and padding to a quota is the defect); inserting the rule between 7 and 8 (every renumber invalidates a reference in `DECISIONS.md`, `docs/ARCHITECTURE.md`, `docs/PROJECT_STATUS.md` and two reports, for nothing); and listing the figures in the JSON contract instead (the contract describes the shape of a reply, not what belongs in it).

**Two new tests, 510 pass.** Covered: the rule is in the map-mode prompt with all five figure names and the per-sentence constraint; rule 8 and the 200-word limit are still there beside it; and the agent prompt carries the same rule, which is the assertion that keeps the two prompts in step.

## D-096 · 2026-10-20 · A semantic claim check, in shadow mode: a second call that reads each sentence against its own clause
**Decision.** After an answer object has passed the structural check, both paths make **one** more call. It is shown each sentence, numbered, with the **full text of the clauses that sentence cites** and nothing else, and asked whether the clause states the sentence. The reply is JSON: `{"verdicts": [{"i": 1, "verdict": "supported" | "partly" | "unsupported", "reason": "…"}]}`. `SUPPORT_CHECK` decides what happens to it:

| mode | what it does |
| --- | --- |
| `off` | no second call at all |
| **`shadow`** | the verdicts go on the response (`support_check`) and into `data/logs/requests.jsonl`. The answer is untouched, whatever they say. **The default.** |
| `enforce` | a sentence judged `unsupported` is dropped; the answer is thrown away with `abstain_reason=unsupported_claims` when the first sentence goes or nothing is left. Implemented and tested, **not enabled.** |

Its call and its tokens are counted in its own record and **not** added to `llm_calls`, so the cost of checking stays separable from the cost of answering. `/api/health` reports the mode.

**Why.** Everything this project validates is structural. `structural_problems` proves that a sentence names a source that was really supplied and that the source exists; **it cannot prove that the clause says the sentence**, and that gap is now measured twice. v1: prompt rules 2 and 6 contradicted each other and 7 of 17 answers carried an unsupported sentence with a marker bolted on (`reports/citation_failures_v1.md`, fixed by D-092). v2: a **100% first-attempt pass rate** alongside `demo-07` still answering a should-abstain question in 60 confident words built out of clauses that do not say it (D-091). Prompt rule 8 asks for exactly this property in words, and nothing checked it. `docs/ARCHITECTURE.md` has carried the limitation as a known one since day 4.

**What makes the second call worth making is that it is a different question.** The answering call is asked "what do these six clauses say about this question?", with the question, the zones, the note and six clauses in front of it. The checking call is asked only "does this clause state this sentence?", with the sentence and its own clause text and nothing else — not the question, not the other sources, not the zones. A test asserts that narrowness by checking the zone description is absent from its prompt. It is still a model checking a model, so it is **evidence and not proof**; what it is not is the same model answering the same question twice.

**Shadow, because a judge nobody has read must not be allowed to delete an answer.** This is the same argument as D-070 for the reranker and D-071 for the abstention threshold: the measurement comes before the behaviour. `reports/live_answers_v3.md` reports the verdict counts and, per case, whether `enforce` **would** have changed the answer — which is a field on the record (`would_change`, `would_abstain`) rather than something a reader has to infer. The lead decides after reading v3. That decision is the one setting the freeze leaves open.

**It never raises, and that is a design property rather than defensiveness.** In `shadow` mode a check that failed must not cost an answer that has already passed every other test. In `enforce` mode it matters more: a check that **could not run has said nothing**, and silence must not be read as a verdict of "unsupported". So every failure — a network error, an unparseable reply, no readable verdicts — is recorded in `error` and the answer stands. Two tests assert exactly that, one per mode, by scripting no reply for the check at all.

**Three more decisions inside it, each the conservative one.**
- **The first sentence is the answer.** `enforce` abstains when sentence 1 is dropped, rather than promoting sentence 2. A reply whose opening claim is unsupported is not a good answer with a bad sentence in it: the sentences after it were written to follow from it, and the result of deleting it is a different answer nobody wrote.
- **`partly` keeps the sentence.** It is the verdict for a figure that is not in the clause or a condition left out — real information for a reader, and not a safe basis for deletion by a judge that has never been checked.
- **A verdict nobody can read never deletes anything.** `enforce` acts on the exact word `unsupported`. An entry whose verdict is some other string is kept in the record as it came — it appears in the counts under its own name — and cannot drop a sentence. A malformed judgement is a malformed judgement, not a conviction.

**Where it lives.** In `app/answer.py`, not a new module: it is step 6 of the answering path, the file's own subject, and `app/agent.py` already imports the validation from there, so both paths run the same two functions (`run_support_check`, `enforce_support`) and `SUPPORT_CHECK` means one thing. The agent's check is given its own `S#` labels and the clauses they resolved to, which a test asserts. `parse_verdicts` accepts a `{"verdicts": […]}` object or a bare list, because the schema in the brief is a list and Groq's JSON mode wants an object, and both now work.

**The cost.** One call per answered question, roughly the answer's sentences plus the full text of the clauses they cite. In v3 that is reported per case, split from the answer's own tokens. An abstention is never checked — nothing was claimed — so the cost falls only on answers.

Rejected: validating semantically **inside** the answer loop and retrying on a bad verdict (that is a second model deciding what the first should have written, and it would hide the disagreement the shadow run exists to show); one call per sentence (n calls instead of one, on a free tier, for a judgement that reads better with the whole answer in view); enforcing from the start (no human has read a single verdict, and an answer deleted by an unchecked judge is worse than an answer with a weak sentence a reader can see); a confidence score instead of three words (it would invite a threshold, and this project already has one provisional threshold waiting on verified questions — D-071); and a new `app/claimcheck.py` module (it would put the two halves of validation in two files and need a CLAUDE.md layout change for no gain).

**Seventeen new tests, 527 pass.** Covered, in map mode: the prompt it builds, with each sentence's own clause text beneath it; `shadow` recording three mixed verdicts and changing nothing, with `would_change` true and `would_abstain` false; `off` making no second call; `enforce` dropping a middle sentence and dropping its citation with it; `enforce` abstaining when sentence 1 goes and when everything goes; a failed check costing nothing in shadow **and** in enforce; a bare list of verdicts being accepted; an unreadable verdict deleting nothing; the check's prompt asking the narrow question and not seeing the zones; and an abstention never being checked. And in agent mode: the same record through the same functions, a dropped sentence, `unsupported_claims` reached from the agent path, a failed check costing nothing, and the checker being shown `S1` rather than `C1`. Plus `/api/ask` and `/api/agent` returning the record, `/api/health` reporting the mode, and the verdict counts reaching the request log.

## D-100 · 2026-10-21 · A final answer Groq threw away is read back, and a provider failure is a 503

**Decision.** Fix round 1, task 1. Three changes, one defect each, all found by the human checks.

1. **The rescue.** `openai/gpt-oss-120b` sometimes sends its final answer in agent mode as a call to a tool named `JSON`, which no ZoneWise request offers. Groq rejects the whole completion with a 400, `code: "tool_use_failed"`, and hands the text back in `error.failed_generation`. `app/llm.py` now reads it: `salvaged_answer` accepts the rejected text **only** when the error is `tool_use_failed`, the text parses as a tool call, the tool is one the request did **not** offer, and its arguments carry `sentences` or `abstain`. It returns the arguments as text, which `GroqLLM._send` hands back as an ordinary `text_response`. Anything else returns `None` and the error stands.
2. **The 503.** `/api/ask` and `/api/agent` catch a provider failure — every `openai.APIStatusError` (400, 429, 5xx), `APIConnectionError` and `APITimeoutError`, and the Anthropic equivalents — and answer `503` with `{"error": "provider_error", "message": "The AI service is busy or returned an error. Please try again in a minute."}`. `web/src/api.js` already shows any `detail.message`, so the interface shows that sentence instead of `Request failed (500)`; `ApiError.isProviderError` tells the two kinds of 503 apart.
3. **The log.** Every failed request now writes one line to `data/logs/requests.jsonl` with `abstain_reason: "request_failed"` and an `error` field holding the exception type and a flattened one-line message. No stack trace, and no key — neither SDK puts the key in an error message.

**Why.** Phase A: the agent failed twice with `Request failed (500)` in the browser on a question the v3 run had answered, and the log held nothing at all about it. Three separate faults sat behind one symptom. The answer had been written and paid for, and was discarded over the envelope it arrived in. A provider's 429 was reaching the user as "something is broken here", which is both wrong and unactionable. And the only record of the whole episode was a screenshot.

**The rescue is deliberately narrow, and deliberately not clever.** It is in `app/llm.py` because that is the only module allowed to know a provider (CLAUDE.md), so `app/agent.py` sees a reply and nothing else — it does not know a rescue happened, and the answer goes through exactly the same parsing, structural check and label validation as any other reply. **No second call is made**, which is the point: the text already exists. The four conditions are each there to stop a different bad rescue: a non-`tool_use_failed` 400 is a different fault; unparseable text is not an answer; **a rejected call to a real tool is not rescued at all**, because fabricating its tool result would invent a retrieval that never ran; and arguments with neither answer field are something else entirely. A rescued answer citing a label the run never issued is still rejected, which a test asserts — the rescue is a different door, not a looser one.

**Why `is_provider_error` matches by name rather than by importing the SDK.** `app/api.py` must not import `openai` or `anthropic` (CLAUDE.md), so the question "did this come from a provider?" is asked in `app/llm.py`, which may. It walks the exception's MRO for a class whose module is `openai` or `anthropic` and whose name is one of the five SDK error base classes. That covers every status error without listing fifteen subclasses, and it costs no import. A `ValueError` of ours is not a provider error and still becomes a 500: "the AI service is busy" must never be the message for a bug in this repository, so our own exceptions are logged and re-raised.

**`tests/test_api.py` builds real `openai` exceptions.** It is the one place in `tests/` that touches `openai`, and it touches only its exception types: the behaviour under test *is* "a real SDK error becomes a 503", and a stand-in exception would pass the test while the real one 500s. The rest of the rescue is tested through `FakeAPIError`, which carries only the fields `salvaged_answer` reads.

Rejected: catching the error in `app/agent.py` (it would put provider logic in the file CLAUDE.md keeps clear of it, and the same fault would still 500 in map mode); asking the model again for the answer in the right shape (a second call for text already in hand, on a free tier, after a failure); treating any 400 as rescuable (Groq's `code` is there to be read, and a parameter refusal is already handled a few lines above); adding `JSON` to the tool list so the call would be accepted (it would make a fake tool part of the contract, and the model would then expect a tool result for it); returning 502 or 429 instead of 503 (503 is already this project's "answers are unavailable, here is why", and the interface already has a path for it — D-050); and logging the traceback (a log that is one JSON object per line stays readable, and the type plus the message is what a reader of `scripts/summarize_logs.py` needs).

**Fifteen new tests, 542 pass.** Covered: the real `failed_generation` from Phase A, replayed, accepted, with its three labels resolved in citation order and no extra call; a rescued answer citing a label the run never issued still rejected; a rejected call to a real tool, a non-answer, unparseable text and a plain 400 all left as failures; arguments nested as a JSON string; the offered tool names read off the payload the SDK was sent; a 429 becoming a 503 with the message; a rejected generation that is not an answer becoming a clean 503; a failed request logged with a one-line `error` and no key; our own `RuntimeError` logged and still a 500; and `is_provider_error` saying yes to three real SDK errors and no to a `ValueError`.

## D-101 · 2026-10-21 · The page sends no referrer; the map tiles send the origin

**Decision.** Fix round 1, task 2. `Referrer-Policy: no-referrer` stays as the page default on every response. The OpenStreetMap tile layer in `web/src/components/MapView.jsx` gains `referrerPolicy="strict-origin-when-cross-origin"`, which Leaflet 1.9 puts on each tile `<img>` as a `referrerpolicy` attribute. An element's own `referrerpolicy` overrides the document's policy for that request alone, so the tiles send `https://<host>/` and nothing else on the page sends anything.

**Why.** Found in Phase B and confirmed in Phase A: OpenStreetMap blocks tile requests that arrive with no `Referer`, and `no-referrer` guarantees none. Dev mode is not affected (Vite serves the page and sets no such header), which is why the app looked fine at `localhost:5173` while the deployed build would have shown "Access blocked" where the map should be.

**The per-layer option is the better of the two fixes, and it exists here.** `leaflet` is pinned at `^1.9.4` and the option has been in Leaflet since 1.7, so the alternative — weakening the whole page to `strict-origin-when-cross-origin` — was not needed. The difference is what the rest of the page does: with the header changed, every outbound request from the app, including the two credit links in the attribution, would carry the origin; with the attribute, exactly one kind of request does, and the default stays at the strictest value. A test pins the leaflet version alongside the attribute, because the attribute would fail silently on an older Leaflet.

**Not verified in a browser here.** This sandbox cannot reach OpenStreetMap, so the change is verified in code and in tests only: the attribute is in the source, it survives `npm run build` into `web/dist`, and the header is still `no-referrer`. The browser check — the deployed build showing map tiles — is listed for Dhruv in `reports/fix_round_1.md`.

Rejected: changing the header to `strict-origin-when-cross-origin` (needed only if the per-layer option were unavailable, and it leaks the origin from every request on the page instead of from the tiles); proxying the tiles through FastAPI (it would make this app a tile cache, re-serve someone else's data under our origin, and cost bandwidth to fix a header); and self-hosting a basemap (a far larger change than the defect justifies).
